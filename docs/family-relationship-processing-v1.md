# 현재 설정의 가족 관계 처리 v1 — GH260

[#260](https://github.com/catchhole-soma/catchhole-backend-java/issues/260)은 이미 현재 프로필에 반영된 가족 관계를 읽어 [#259 관계 모델](family-relationships-v1.md)에 연결한다. 기존 추출 프롬프트·출력 스키마·LLM 호출·토큰 차감은 변경하지 않는다. 별도 규칙 후처리에서 명확한 새 명제를 자동 연결하고, 모호한 명제는 후보 검토로 남긴다. 원문 전체나 CharacterFact 이력에서 관계를 다시 추출하지 않는다.

## 명시적 조상 문법 — GH261

`아르덴의 5대손`, `아르덴의 5대손이다`, 현재 소유자가 비칼일 때 `아르덴의 5대손 비칼`/`아르덴의 5대손인 비칼`을 `DESCENDANT_OF`, generationGap=5로 읽는다. `아르덴의 후손`, `조상: 아르덴`, `선조: 아르덴`은 세대 수 null의 DESCENDANT_OF이며 `아르덴의 조상`/`후손: 아르덴`은 ANCESTOR_OF다. 확정 및 미등록 표시 방향은 조상→후손으로 정규화한다. 현재 프로필에 있는 조상 명제는 기본 CURRENT이며 단순히 오래전 인물이라는 이유로 HISTORICAL로 바꾸지 않는다.

이름 접미사는 현재 소유자와 완전히 일치할 때만 읽는다. 다른 인물을 서술하는 접미사, 중첩 소유격, 가문·혈통·집단, 0/음수/범위 초과 세대 수, 지원하지 않는 `N세손`은 자동 관계로 바꾸지 않는다. `후손이 아니다`와 `후손일지도 모른다`는 기존 NEGATED/UNCERTAIN 검토 규칙을 유지한다. 이름 일부에 우연히 `왕조`/`클랜`이 포함된 왕조현·클랜시는 집단으로 오인하지 않는다. 중간 인물이나 직접 부모는 생성하지 않고 기존 Fact 근거를 그대로 연결한다.

같은 대상·시점에 서로 다른 명시 세대 수가 있으면 CONFLICTING으로 보류한다. 알려진 부모 경로와 조상 세대 차이가 맞지 않으면 GENERATION_GAP_CONFLICT로 보류한다. 미상 세대 수와 알려진 세대 수는 별도 명제이며 자동으로 구체화하거나 합치지 않는다. 등록되지 않은 조상도 명시성·현재성·상충 검사에 통과한 후보만 MENTION으로 표시한다.

## 입력과 지원 문법

입력은 활성 캐릭터의 실제 현재 PROFILE 슬롯과 `CharacterSnapshotSource`에 함께 남아 있는 Fact다. `RelationshipSourceResolver`가 제공하는 전체 `{factValue, valueJson}`와 해당 슬롯의 모든 출처를 사용한다. 여러 Fact가 한 슬롯에 기여하면 예전 Fact 문자열 각각을 파싱하지 않고 현재 슬롯을 한 번만 읽는다. 직접 수정한 현재 설정도 같은 경계를 사용한다.

`ExplicitFamilyRelationshipParser`는 `factValue`와 문자열 `valueJson`, 또는 `valueJson.value`만 읽는다. 같은 두 표현은 한 번만 파싱한다. 두 표현이 다르면 `CURRENT_VALUE_CONFLICT`로 보류하며, 그중 하나를 임의로 선택하지 않는다. 직접 편집 API가 저장하는 `valueJson={value, name}`도 지원한다. `name`은 비어 있지 않은 문자열이며 마지막 `.` 뒤 factKey suffix의 `_`를 공백으로 바꾸고 공백을 축약한 표시명과 같거나, `family`·`가족`·`가족 관계`·`가족관계` 중 하나여야 한다. 키와 일치해도 추정·추측·불확실·소문·비유·부정·거짓·가능성·가설·의심·믿음이나 과거·예정 등의 알려진 확실성/시점 한정어가 들어 있으면 보류한다. `name`에서 관계 명제나 상대를 추출하지 않는다. 불일치·비문자 표시명, `value`와 허용된 `name` 외 속성, 지원하지 않는 구조는 그 의미를 생략한 채 자동 처리하지 않고 `UNSUPPORTED_STRUCTURED_CONTEXT`로 보류한다. 원문 인용, 임의 중첩 JSON, 과거 Fact는 파서 입력이 아니다.

| `홍길동의 아들이며 김철수의 형제` | CHILD_OF + SIBLING | 완결된 모든 절을 읽고, 일부 미지원 문맥이 있으면 전체 검토 |
| `아버지: 그 사람` / `아버지: 미상` | 미지원 | 대명사나 미상 호칭을 실제 이름으로 연결하지 않음 |
| `아버지: 사망` / `아버지: 고향에서 살고 있음` | 미지원 | 상황 서술을 상대 인물 이름으로 만들지 않음 |
| `청연 가문의 직계` | 가족 표현 발견, 관계 없음 | 혈통을 특정 부모 관계로 바꾸지 않음 |
| 스승 항목의 `백운 할머니` | 가족 관계 아님 | 인명 뒤의 일반 호칭만으로 조모 관계를 만들지 않음 |

현재 설정 편집 API는 `profile.<항목명>` 형태를 사용하며, `CharacterServiceImpl.normalizeSettingKey`는 항목명의 공백을 `_`로 저장하고 `keySuffixDisplayName`은 이를 공백으로 표시한다. 따라서 파서는 `_`를 namespace 구분자로 사용하지 않는다. `profile.`와 기존 공유 fixture의 `profile_family/` prefix만 제거한 뒤 전체 항목명의 `_`를 공백으로 복원한다. 항목명 내부의 추가 `.`나 `/`도 버리지 않는다. 지원 역할과 정확히 일치하는 `전 남편`은 기존 과거 역할을 사용하고, `과거 아버지`·`추정 아버지` 같은 미지원 가족 항목명은 `UNSUPPORTED_FAMILY_SYNTAX`로 보류한다. 값이 단순 이름이면 유형을 추측해 후보를 만들지 않으며, 값 자체에 완결된 명제가 있더라도 해당 보류 사유를 유지한다. `valueJson.name="family"` 같은 일반 표시명도 키의 한정어를 취소하지 않는다. `profile_아버지`처럼 알려진 prefix가 아닌 문자열을 마지막 `_`에서 나누는 동작은 지원하지 않는다.

가족 명제는 `가족관계` 항목에만 한정하지 않는다. 현재 `출생 순서`나 `특징` 항목의 값에서도 같은 문법을 읽는다. 소유격의 자녀 역할 앞에는 `첫째`부터 `열째`, `첫 번째`부터 `열 번째`, 숫자 1–999의 `제2`·`2번째`·`2째` 형식과 `외동`·`막내`·`맏`을 허용한다. `장남`·`차남`은 아들, `장녀`·`차녀`는 딸 호칭으로 읽으며 반대편 부모의 성별을 추론하지 않는다. 이 수식어 규칙을 부모·배우자 역할 앞에 적용하거나 서수로 다른 가족 구성원을 생성하지 않는다.

`형`·`오빠`·`누나`·`언니`·`동생`·`남동생`·`여동생`은 단순 상대명의 소유격으로 관계가 명시된 경우 ASSERTED다. `동생: 현우` 같은 역할 표기는 여전히 친근한 호칭일 수 있어 UNCERTAIN으로 검토한다.

상대 표현이 독립된 단어 `남성`·`여성`·`남자`·`여자`·`사람`·`인물`로 끝나는 설명이면, 형제뿐 아니라 부모·자녀·배우자 역할에서도 AMBIGUOUS_FAMILY_ROLE로 검토한다. 소유격·역할 표기·항목명에서 역할을 보완하는 입력에 같은 기준을 적용한다. 같은 문구의 활성 캐릭터가 있어도 자동 확정하지 않으며, 새 미등록 후보도 가계도에 바로 표시하지 않는다. 명시된 부정·비유·추측은 원래 판정을 유지하고, `김남성`처럼 해당 어휘가 인명 일부인 경우는 설명형으로 판단하지 않는다. 이는 이름의 실재 여부를 보장하는 규칙이 아니며 등록 인물의 정확한 연결은 별도 검증한다.

관계 뒤의 설명은 `인 [등급/레벨 수식] 직업명` 형태로 제한한다. 등급/레벨은 선택이며 1–999의 `6등급`·`6레벨`·`레벨 6`을 지원한다. 직업명은 탐험가·모험가·전사·기사·검사·마법사·사제·궁수·상인·학자·연금술사·치유사이며 끝의 `이다`·`입니다`·`임`을 허용한다. `인 줄 알았으나 아니었다`, `인 척하는 탐험가`, `인 탐험가이며 다른 사람의 딸` 같은 추가 서술은 잘라 버리지 않고 미지원으로 남긴다. 사망·실종·모름·거주 등 알려진 상황 표현이나 `에서`·`에게`·`처럼` 등의 서술 표지가 있는 문자열도 상대 이름으로 받지 않는다. 따라서 `학교에서 만난 은하의 언니`의 앞부분 전체를 인명으로 만들지 않는다.

문법은 전체 명제에 일치해야 한다. 줄바꿈과 세미콜론은 명제 구분자로 지원한다. GH278은 쉼표 및 지원 역할 바로 뒤의 `이자`·`이며`·`이고`로 연결된 명시적 절과 `민준과 서연의 어머니` 같은 공동 상대를 추가한다. 모든 절과 상대를 검증하며, 임의의 복잡한 소유격·서술·시점을 추론하지 않는다. 복문 뒤의 부정·추측·과거가 앞부분까지 수식할 수 있으면 일부만 확정하지 않는다. 나뉜 문장 중 해석하지 못한 부분이 있으면 이미 파싱한 명제도 `UNSUPPORTED_FAMILY_SYNTAX`로 보류한다. 예를 들어 `아버지: 홍길동; 사실은 그렇지 않다`에서 앞부분만 자동 확정하지 않는다. 의형제와 만남·동행·감정 표현은 가족 관계를 만들 근거가 아니다. 가문·혈통·직계·친척 및 명시적인 조부모·삼촌 등의 표현도 가족 정보로 발견하지만 현재 지원하는 관계 종류에 억지로 대응시키지 않는다.

표현 채널 하나당 4,096자, 구분된 명제 20개를 넘으면 전체를 보류한다. 출처가 20개를 넘는 슬롯도 앞의 20개만 잘라 쓰지 않는다. 가족 표현은 있으나 명제를 만들 수 없는 슬롯은 `unsupportedSourceCount` 안내 대상이며, 임의 유형의 후보를 만들지 않는다. 이 수치가 0이라고 모든 한국어 가족 서술을 해석했다는 뜻은 아니다. 지원 문법 밖 표현의 의미적 재현율은 측정하지 않았다.

파서 결과와 문법 예시는 [공유 fixture](contracts/family-relationship-processing-v1.json)의 40개 합성 사례와 `ExplicitFamilyRelationshipParserTest`가 함께 검증한다. `ExplicitFamilyRelationshipCorpusTest`는 관찰한 현재 13개·이력 4개 문장 유형을 합성 인명과 문장으로 재현한다. 현재 13개 중 11개는 명시적 관계, 1개는 설명형 상대의 검토 대상, 1개는 스승에게 붙인 일반 호칭이다. 17개 모두가 가계도 간선 대상이라는 뜻은 아니다. 이력에만 남은 명시 관계가 문법상 읽혀도 후처리는 현재 슬롯과 출처에 함께 남은 Fact만 입력으로 사용하며 과거 관계를 자동 복원하지 않는다. 이들 문법 fixture는 이름 연결·소유권·순환 검증 이전의 계약이다.

## 명시 표현 보완 — GH278

- 가족 항목에서 `양아버지 민준`, `아들 서연`, `외동아들 민준`처럼 역할을 먼저 쓰는 형식을 읽는다. 역할 없는 영문 항목의 값만으로 인물을 추론하지 않는다. `동생 민준` 등의 친근 호칭은 기존 UNCERTAIN 정책을 유지한다.
- `민준과 형제 관계`, `민준의 쌍둥이 동생`, `민준의 오라버니`, `민준의 서녀`를 기존 관계 종류에 대응시킨다. 쌍둥이로 부모·나이·성별을 추론하지 않으며 서녀의 별도 신분 subtype도 생성하지 않는다.
- `profile.막내아들` 같은 자녀 수식어 키를 지원한다. 부모·배우자 앞에 자녀 수식어를 붙이거나 출생 순서에서 다른 형제를 생성하지 않는다.
- `민준의 둘째 딸 서연`의 끝 이름은 현재 소유자가 정확히 `서연`일 때만 허용한다. 축약명·다른 인물·이름 뒤 부정문을 일치로 간주하지 않는다.
- 가문·세가 자체를 개인으로 연결하지 않고, 공동 상대의 상황 설명·선택·부정 범위를 자르지 않는다. 모든 확정에는 기존 출처·이름 연결·상충·순환 검증이 이어진다.

실제 미지원 78건의 의미별 분류와 변경 전후 진단 범위는 [GH278 진단 기록](family-relationship-coverage-gh278.md)을 따른다. 추가 인식 수는 확정 관계 수가 아니다.

## 정확한 상대 연결과 자동 확정

파서는 캐릭터 ID를 선택하지 않고 상대 호칭을 반환한다. 후처리는 같은 작품의 활성 캐릭터 중 앞뒤 공백을 제거한 이름이 정확히 일치하는 사람을 찾는다. 내부 공백·대소문자·별칭·유사 이름을 정규화하거나 추정하지 않는다. 일치 0명은 UNRESOLVED_TARGET, 여러 명은 AMBIGUOUS_TARGET, 자기 자신은 SELF_REFERENCE로 검토한다.

다음 조건을 통과한 **이번 처리에서 처음 만들어진 후보**만 자동 확정한다.

1. 현재 프로필과 출처 토큰이 유효하고 파서가 전체 명제를 지원한다.
2. 단정된 관계이고 상대가 정확히 한 명으로 연결된다. UNKNOWN 시점·부정·비유·불확실성은 보류한다.
3. 동일한 관계·시점에 대한 명시적 긍정과 부정의 충돌이 없고, 현재 부모 그래프와 이번 처리 후보를 합쳐도 순환하지 않는다.
4. 같은 정규화 관계가 이전에 철회된 이력이 없다. 철회한 관계는 새 출처가 생겼다는 이유만으로 자동 복원하지 않는다.

부모/자녀 방향과 배우자/형제의 대칭 정규화, 세부 유형·서사 시점의 구분은 #259 규칙을 그대로 사용한다. 모르는 부모 생성, 최대 부모 수 제한, 형제로부터 부모 역산, 감정의 양방향 추정은 하지 않는다. 사람 검토 없이 일반 자연어의 모든 모순을 판별하는 기능은 아니다.

후보의 `origin=CURRENT_SETTING_RULE`과 `automaticallyConfirmed`로 생성·확정 경로를 구분한다. 사용자가 만든 후보는 `origin=MANUAL`이며 기존 명시적 확정 API를 유지한다. 자동 처리의 검토 사유는 후보 `reviewReasons`에 함께 노출한다.

가계도 끝점 표시를 위해 parser 결과에는 문법에서 직접 읽은 subjectRole/objectRole도 보존한다. 이는 현재 지지 근거와 저장 관계를 대조하는 읽기 전용 표시 정보이며 자동 후보 request hash, 관계 canonical key, 저장 명제 또는 LLM 책임에 추가하지 않는다. 서로 다른 호칭의 같은 명제는 표시 시 상충 판단을 위해 보존하되 기존 처리기의 requestId 방문 집합으로 한 후보만 저장한다. 자세한 호칭·중립 대체 규칙은 [가계도 계약](family-tree-v1.md)을 따른다.

## 저장 이후의 별도 처리와 버전

```mermaid
flowchart TD
    A["기존 프로필·출처 또는 인물 이름·보관 상태 변경"] --> B["같은 저장 트랜잭션에서 작품의 관계 입력 버전 증가"]
    B --> C["기존 설정 저장 완료"]
    C --> D["별도 후처리가 작품 행 잠금 획득"]
    D --> E["최신 현재 슬롯·활성 캐릭터·기존 검토 결정 조회"]
    E --> F["지원 문법·정확한 상대·충돌·순환 검사"]
    F --> G["새 후보 자동 확정 또는 검토 보류"]
    G --> H["기존 자동 확정 근거 재검증과 완료 버전 저장"]
    D --> I["실패하면 관계 처리만 롤백"]
    I --> J["별도 트랜잭션에서 실패 코드와 재시도 시각 저장"]
```

### 상세 처리 기준

- PROFILE 출처 교체·병합·제거, 캐릭터 발견/연결과 이름 변경·보관·복구에서 `works.relationship_input_version`을 증가시킨다. 관계 후처리 때문에 기존 설정 저장이나 분석 완료를 롤백하지 않는다.
- `relationship_processing_states`는 작품별 처리 완료 버전, 시도 버전, 완료 시각, 정제된 실패 코드, 재시도 시각 및 마지막 처리 집계를 저장한다. 모든 처리 쓰기는 기존 설정 변경과 같은 Work 행 잠금을 사용한다.
- 스케줄러는 기본 10초 간격으로 최대 10개 대기 작품을 처리한다. 실패한 작품은 기본 1분 뒤 재시도하며, 더 새로운 입력 버전은 이전 실패의 대기를 넘어서 처리할 수 있다. 이 설정은 처리량 또는 완료 시간 보장이 아니다.
- 대기 작품 조회에서 작품 ID와 입력 버전을 함께 읽고, 처리와 별도 실패 기록에 같은 버전을 전달한다. Work 잠금 획득 전에 입력이 바뀌면 해당 큐 항목은 건너뛰고 다음 조회가 새 버전을 처리한다. 처리 롤백/커밋 실패 이후 새 설정이 저장됐거나 같은 버전의 다른 처리가 이미 완료됐다면 늦은 실패 기록은 무시한다. 새 입력을 시도하지도 않고 FAILED로 표시하거나 이전 실패의 재시도 대기에 묶지 않는다.
- 원래 설정·출처·명제가 같은 규칙 후보의 요청 ID는 재실행해도 같다. 실제 상대 연결 결과를 이 ID에 넣지 않아, 상대가 나중에 등록되거나 동명 수가 달라져도 새 후보를 만들어 이전 검토 결정을 우회하지 않는다.
- 형제 호칭 규칙 확장이나 같은 슬롯의 미지원 문법 해소로 명제의 파서 결과가 UNCERTAIN에서 ASSERTED로 바뀌면, 새 ASSERTED 요청 ID에 후보가 없을 때 동일 원본 명제와 출처 토큰·Fact 집합으로 UNCERTAIN 요청 ID도 대조한다. 그 ID의 `CURRENT_SETTING_RULE` 후보가 있으면 그대로 재사용한다. 현재 후보 필드가 사용자에 의해 다른 상대나 관계로 수정되어도 원래 요청 ID로 찾으므로 기존 대기·수정·제외·수동 확정·철회 결정과 버전을 유지한다. 같은 출처의 다른 명제나 독립된 새 출처까지 일괄 차단하지는 않는다.
- 기존 PENDING 후보는 자동 확정하지 않는다. 처음 미해결이던 상대가 나중에 등록돼도 기존 후보의 연결·명제를 자동 수정하지 않으며, 연결을 원하면 사용자가 선택한다. #261 가계도는 현재 출처와 명시성이 검증된 미등록 후보를 MENTION으로 표시하므로 등록 캐릭터 연결은 필수가 아니다. 사용자가 수정·확정·제외한 동일 입력 후보도 덮어쓰거나 되살리지 않는다.
- 기존 자동 확정 후보는 새로 확정하지 않고 현재 이름 연결, 명시적 충돌과 순환을 다시 검사한다. 유효하지 않으면 검토 사유를 기록하며 이전 관계와 근거 이력은 보존한다.
- 부모 순환 검사는 대상 변경·명시적 상충 등 다른 보류 사유를 먼저 판정한 뒤 수행한다. 현재 수동 근거가 지지하는 부모 관계와, 이번 검증을 통과한 새 명제·기존 자동 확정 명제 전체로 같은 그래프를 만들어 순환에 속한 간선을 함께 보류한다. 무효인 자동 명제를 순환 경로로 쓰지 않으며, 같은 관계의 독립적인 유효 수동·자동 근거는 유지한다. 기존 PENDING 후보를 자동 해결하지 않는 규칙은 그대로다.
- 프로필 입력이나 인물 상태가 바뀌면 기존 자동 근거의 `validatedInputVersion`은 최신 작품 버전보다 뒤처진다. 재검증 완료 전에는 그 근거를 유효한 자동 지지로 사용하지 않는다. 원래 토큰이 같은 자동 관계도 재처리 대기 중에는 REVIEW_REQUIRED가 될 수 있다. 수동 확정 근거는 자동 버전 대기 때문에 차단하지 않는다.
- 입력 내용이나 출처 집합이 실제로 바뀌면 다른 규칙 후보가 만들어질 수 있다. 동일 입력의 사용자 결정 보호가 앞으로 들어오는 모든 다른 설정까지 일괄 제외한다는 뜻은 아니다.
- 기존 데이터는 배포 즉시 원문을 전수 분석하지 않는다. 현재 설정 변경이나 사용자의 처리 요청으로 작품 단위 후처리를 시작한다.

자동 후보 하나의 입력 출처는 해당 현재 슬롯에 기여한 Fact 전체다. 원문 `hasEvidence`와 관계 근거의 현재성은 별개다. 원문 파기로 인용이 없어져도 현재 값과 출처가 남아 있으면 관계 해석 입력은 유지된다. 현재 설정에서 빠진 과거 Fact는 원문이 남아 있더라도 새 관계 생성 입력으로 쓰지 않는다. 원문 보기·파기·보관 캐릭터의 조회 제한은 기존 Fact evidence API를 따른다.

## API와 검토 화면 연결

모든 API는 JWT와 작품 소유권을 요구한다. 처리 API는 `/api/v1/works/{workId}/relationship-processing`이다.

| 메서드 | 결과 |
| --- | --- |
| GET | `NEVER_PROCESSED`, `PENDING`, `SUCCEEDED`, `FAILED`와 현재/완료 버전, 완료 시각, 실패 코드, 재시도 시각 및 집계 |
| POST | 현재 설정의 처리를 요청하거나 실패 후 재시도. 이미 대기 중이면 같은 대기를 공유하며 AI 재분석을 시작하지 않음 |

`autoConfirmedCount`는 마지막 처리에서 **새로 자동 확정한 후보 수**이며, 작품 전체 관계 수가 아니다. `reviewRequiredCount`는 마지막 처리에서 현재 설정과 대응된 PENDING 후보 수다. `unsupportedSourceCount`는 가족 표현을 발견했지만 후보로 해석하지 못했거나 출처 상한을 넘은 슬롯 수다. 실제 검토 상태·상대·명제는 기존 `/relationship-candidates` 목록과 상세를 기준으로 조회한다.

검토 화면은 처리 상태·근거·보류 사유를 표시하고, 필요한 경우 상대와 관계 명제를 수정한 뒤 기존 수정/확정/제외 API를 사용한다. stale 토큰이나 버전 충돌이 나면 최신 후보와 source API를 다시 읽는다. 사용자가 처리 버튼을 다시 눌러도 기존 대기 후보가 자동으로 해결되는 것은 아니다. 자동 확정 후보는 기존 `/relationships`에서 읽으며, 확정 관계에 대한 `visibleInFamilyTree` 계약을 유지한다. #261의 미등록 언급 표시는 별도 `displayableAsMention` 계약으로 구분하며 불확실·상충 관계를 확정 관계처럼 노출하지 않는다. 그래프 배치와 가계도 화면은 #261에서 담당한다.

## 검증 범위

순수 파서 테스트는 역할 방향, 세부 유형, 부정·추정·비유, 대명사, 두 현재값 채널의 충돌, 미지원 문맥, 중첩 JSON 미접근 및 입력 한도를 검증한다. 공통 fixture 40건도 같은 production 파서로 실행한다. 통합 테스트는 현재 설정 저장의 버전 전달, 규칙 후보 생성·재처리·사용자 결정 보호, 이름 연결 변화, 충돌·순환, 자동 근거 재검증과 실패 복구를 검증한다. 실행 결과와 PostgreSQL/Flyway 적용 확인은 실제 완료한 검증 기록을 기준으로 보고한다. 이 문서 자체가 모든 문법의 의미 정확도나 대규모 작품의 처리 성능을 보장하지 않는다.
