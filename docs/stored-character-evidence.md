# 저장된 캐릭터 근거와 원문 참조 수명

관련 이슈: [#363](https://github.com/catchhole-soma/catchhole-backend-java/issues/363)

## 문제와 변경

회차를 삭제하고 같은 번호로 다시 올리면 이전 분석 Job의 key/hash는 이력에 남지만 S3 객체는 파기됩니다.
확정된 캐릭터 Fact를 새 비교 문맥에 담는 과정에서 이 옛 경로를 다시 읽으면, 새 회차의 추출이 정상이어도 캐릭터 비교 준비가 실패했습니다.
특히 `{factTime:null,referenceTime:null}`도 원문 검증 경로로 들어갈 수 있었습니다.

V112 이후 비교는 후보를 저장할 때 DB 청크로 확인한 결과를 재사용합니다. 비교 준비와 S3 가용성의 결합을 없애고, 원문의 삭제 여부는 별도로 명시합니다.
확정값을 지우거나 삭제한 원문을 새 원문으로 대체하지 않습니다.

## 데이터 흐름

1. Python은 기존대로 1차 추출 인용을 실제 청크의 quote/offset으로 확정한 뒤 후보를 저장합니다.
2. PostgreSQL의 후보 BEFORE 트리거는 저장된 청크, 작품/회차 또는 설정집 revision, Job의 key/version/hash 결속을 확인합니다. 인용과 시점·부모 프로필 인용을 Unicode code point 위치로 대조해 `stored_evidence_validation`을 생성합니다. 네트워크 호출은 없습니다.
3. Java는 후보 입력 JSON과 검증 당시 원문 정보가 현재 기록과 같은지 확인하고 검증 결과를 비교 문맥에 넣습니다. 비교 시 S3나 청크 전문을 다시 읽지 않습니다.
4. 삭제/교체 요청 INSERT의 AFTER 트리거는 같은 트랜잭션에서 이전 Job의 `source_reference_invalidated_at`을 채웁니다. 요청이 롤백되면 무효화도 롤백됩니다. retained key를 가리키는 새 Job은 제외합니다.
5. 기존 파기 처리기가 S3와 파생 근거를 정리합니다. 그 전 재시도 대기 중에도 읽기에서는 이전 출처를 `SOURCE_EVIDENCE_PURGED`로 처리합니다. 요청이 지워져도 Job의 무효화 표시는 남습니다.

과거 key/hash는 감사 메타데이터로 남습니다. 삭제된 출처의 비교 입력에는 `storageBinding`을 넣지 않습니다.
확정 Fact 값과 대표 시점 설명은 유지하지만, 대표 시점 복사본에 남은 인용도 전달하지 않습니다.

대표 시점의 **서버 내부 고정값**은 DB의 원래 값과 같게 유지합니다. 승인 시 `expectedCurrent`를 실제 현재값과 비교하기 위한 기준이므로, 근거 표시 정책으로 바꾸지 않습니다.
미검증 시점 인용은 비교 문맥과 누적 claim을 만드는 **모델용 투영**에서만 제거합니다. 일반 묶음 비교 완료도 모델에 전달한 복사본이 아닌 서버 문맥의 시점으로 선택을 기록합니다.
따라서 오래된 인용이 인증되지 않아도 검증된 새 관측으로 시점을 갱신할 수 있고, 비교 이후 실제 시점이나 근거가 변경되면 기존 정확 일치 검사로 적용을 막습니다.
원문 파기는 서버 고정값·선택 기록의 인용도 기존 정리 경로로 제거합니다.

## 검증과 예외

- 인용과 후보 입력을 구조적 JSON 배열로 결속합니다. 입력이 바뀌면 검증을 다시 생성하고, 상태만 바뀐 JPA 전체 UPDATE는 원 기록을 유지합니다. 재청킹으로 옛 청크 UUID가 사라져도 이미 확인한 결과를 재사용합니다.
- 일반 인용과 확정된 설정집 인물의 추가 프로필 인용은 입증되는 구절만 전달합니다. 이미 확정한 인물의 미검증 인용 때문에 비교를 중단하지 않으며, 신규 자동 승격의 별도 동일인 증명 검증은 유지합니다. offset 누락·불일치·다른 청크·문자열 숫자·camel/snake 충돌은 인증하지 않습니다.
- 시점 인용을 입증할 수 없으면 그 시점 근거를 제외합니다. 새 비교 후보에도 검증된 시점만 전달하므로 검증 불가 시점을 새 대표 시점으로 승격하지 않습니다. 명시적인 양쪽 null은 원문 조회가 필요 없습니다.
- 잘못된 작품/소유권/manifest, 잘못된 시점 JSON 구조, 검증된 referenceTime과 저장된 대표 시점의 불일치 등 계약 오류를 정상 근거로 간주하지 않습니다.
- 기존 데이터는 실제로 남아 있는 현재 출처 청크로만 backfill합니다. 청크가 없으면 S3로 보완하거나 인용을 인증하지 않습니다. 따라서 일부 과거 인용이 비교 입력에서 제외될 수 있으나 확정값은 유지됩니다.
- 검증 기록은 내부 파생 데이터입니다. Python ORM은 컬럼을 몰라도 기존 저장 코드를 계속 쓸 수 있고, Java의 매핑은 insertable/updatable=false입니다. API payload 필드와 모델·토큰 차감 정책은 바뀌지 않습니다.

## 유지되는 원문 조회

사용자가 원문을 여는 상세/미리보기, 1차 추출, 설정집 자동 확정의 검증 등은 실제 원문이 필요합니다.
이 PR은 그 경로를 없애지 않습니다. 미리보기의 manifest 조회에는 무효화 확인을 추가합니다.
현재 분석의 lease, source 변경, 작품 잠금, 고정 문맥과 확정 검증도 유지합니다.

## 검증 방법

`StoredCharacterEvidencePostgresIntegrationTest`는 전용 pgvector PostgreSQL 16에서 전체 Flyway와 JPA validate를 실행합니다.
저장 시 Unicode 인용·시점 검증, 잘못된 인용/청크 거절, 재청킹 후 재사용, 직접 검증 기록 변조 방지, 삭제 접수/롤백/재시도,
교체의 retained key, source version 변경, V111→V112 이관을 검사합니다. 비교 및 무효화된 미리보기에서 S3 호출이 없는지도 확인합니다.
단위 테스트는 현재/이력/대표 시점과 설정집 identity 문맥, 양쪽 null 시점, 파기 대기 중 복사본 인용 제외를 검사합니다.
기존 시점의 검증 기록이 없을 때 capture→모델 투영→선택 저장→실제 승인으로 새 시점이 반영되는지, 일반·누적 묶음의 기준값과 claim 인용 제외가 함께 유지되는지도 검사합니다.
실제 운영 데이터 수정·실제 LLM 호출·배포는 이 검증에 포함하지 않습니다.
