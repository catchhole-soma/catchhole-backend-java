# GH215 검토 화면의 캐릭터 결정 저장

캐릭터 연결 수정은 이미 `userModified`로 저장되었지만 공개 응답에는 이 값이 없었다. 화면이 React Set으로 별도 확인 여부를 기억해 새로고침 뒤 다시 확인해야 했고, 서버에서는 연결 수정과 내용/시점 판단을 구분하지 못했다.

완료된 `ORDERED_PROVISIONAL` 및 단일 회차 `MANUAL + CONFIRMED_ONLY` 후보는 기존 내용 수정 PATCH에 선택값을 함께 보낸다.

```json
{
  "attributeName": "profile.affiliation",
  "attributeValue": "왕실 기사단",
  "reviewedApplicationMode": "APPLY_PROPOSAL",
  "expectedUpdatedAt": "화면 응답의 updatedAt"
}
```

- `APPLY_PROPOSAL`: 작가가 확인한 이 값을 현재 설정에 반영하겠다는 선택이다. 초안에서는 원래 시간 의미를 보존하고 최종 확정 시에만 `PRESENT`로 적용한다. 다른 선택으로 되돌릴 때 원문 시점이 바뀌지 않게 하기 위함이다.
- `HISTORY_ONLY`: 현재값은 유지하고 후보 값을 원문 회차 이력으로 남긴다. 이력 저장 자체가 과거라는 단정은 아니므로 원래 시간 의미를 보존한다.
- 단일 회차 수동 검토에서 모드를 생략하고 값을 편집하면 이전 저장 방식을 유지하거나 기본 현재 반영으로 최종 초안을 저장한다. 다른 후보의 제안을 무효화하거나 비교 Job을 만들지 않는다. 완료된 누적 분석의 모드 생략은 기존 값 편집 동작을 유지한다.
- 응답의 `userModified`는 내용/연결 수정, `reviewedApplicationMode`는 확정할 값에 대한 저장된 선택이다. 전자만 보고 검토 완료로 판단하지 않는다.
- 선택을 저장한 뒤 값이나 대상을 바꾸면 이전 선택을 해제한다. 순수 대상 연결에서 원본 후보 값과 AI의 검증된 제안 값이 같고, 독립 ADD이거나 같은 대상이며, 시점이 알려져 있고 의존성이 없을 때만 안전한 기존 판단을 이어받는다. 같은 대상을 다시 골라도 MERGE 제안 문장과 원본이 다르면 검토 완료로 만들지 않는다.
- 편집으로 AI 제안이 무효화되었더라도 저장한 수동 초안을 `PENDING`으로 표시해 가짜 분석 대기를 만들지 않는다. 이 경우만 비교 상태를 `NOT_REQUIRED`로 두며 원래 성공/실패 상태와 근거는 보존한다.

확정 요청에는 기존 `applicationMode`, `applyEditedValue=true`와 마지막 응답의 `expectedUpdatedAt`을 보낸다. 그룹도 후보마다 동일하다. 서버는 다음을 확인한다.

1. 작품 소유권·원문 보존 및 버전·활성 순차 분석 잠금.
2. PATCH 시 화면 후보 시각, 유효한 schema/값, 완료·sealed된 실행, 해소된 캐릭터, 격리 가능한 실패 종류.
3. confirm 시 마지막 선택의 모드와 후보 시각. 다른 탭이 새 초안을 저장한 경우 낡은 화면에서 확정할 수 없다.
4. 현재값 반영 시 선택 시점의 실제 snapshot version. 선택 뒤 현재값이 달라졌다면 새로 확인하도록 409를 반환한다.
5. 기존 후행 회차·직접 수정·삭제·동일 회차의 현재값 보호. 현재 반영을 골라도 보호해야 하는 현재값은 덮지 않고 이력으로 확정할 수 있다.

현재값은 실제 확정에서 잠근 최신 대상에 schema 검증을 다시 적용한다. AI의 옛 병합값이나 부수 삭제를 재사용하지 않고 작가가 확인한 후보 값을 사용한다. 세계관의 `MERGE` 역시 최종 제출 `value`를 그대로 저장하므로 프론트의 합친 문장 미리보기와 제출값을 일치시킨다. 새 LLM 호출은 추가하지 않는다.

숫자 편집은 Hibernate JSON의 DecimalNode/IntNode 차이로 flush 뒤 다시 dirty로 인식될 수 있다. PATCH는 flush 후 저장 상태를 refresh해 응답 `updatedAt`이 실제 커밋 값과 같게 한다. 해당 회귀는 응답 시각·재조회 시각의 일치와 즉시 확정 성공을 함께 검증한다.

V72는 nullable 컬럼 두 개만 추가한다. 기존 `user_modified` 행을 검토 완료로 소급 보정하지 않는다. Python Worker는 이 컬럼을 쓰지 않으며 신규 INSERT에서 생략해 NULL로 두므로 기존 SQLAlchemy 매핑과 호환된다.

## 합성 데이터로 브라우저 확인

운영·기존 로컬 DB를 쓰지 않는 선택적 H2 HTTP 테스트 서버:

```sh
GH215_REVIEW_RUNTIME=true ./gradlew test --tests '*ReviewUxHttpRuntimeTest' --rerun
```

API는 `127.0.0.1:18081`, fixture는 권한 600의 `/tmp/gh215-review-runtime.json`에 저장한다. 파일에는 테스트 계정 인증 정보가 있으므로 로그·보고서에 출력하지 않는다. 세계관 범위 선택/신규/병합과 캐릭터 시점 판단/정상 추가/미상 연결을 제공한다. `touch /tmp/gh215-review-runtime.stop`으로 종료하거나 30분 후 자동 종료한다. 일반 CI에서는 환경변수가 없어 건너뛴다.


## 배포 순서와 호환 범위

백엔드 V72 migration 및 검토 결정 API와 새 프론트를 같은 배포 단위로 반영한다. 스키마 추가는 nullable이므로 기존 Worker INSERT에는 영향이 없지만, 이전 프론트에서 완료된 누적 분석의 수정 후보를 `applyEditedValue=true`만 보내던 확정은 새 서버에서 거절된다. 기존 `userModified`를 검토 완료로 추정하면 대상 연결만으로 시점 판단을 우회할 수 있어 호환 우회를 넣지 않았다. 배포 후 열려 있던 검토 화면은 새로고침해 최신 UI에서 현재값/이력 선택을 한 번 저장해야 한다. 완료된 단일 회차 수동 편집도 `expectedUpdatedAt`을 요구하므로 최신 프론트와 함께 배포한다. 구형 그룹 확정은 플래그가 없으면 기존 revision 경로를 사용한다.

## 실제 수동 검수에서 발견한 비교 대기 문제

2026-10-02 로컬 새 작품을 회차별 `MANUAL + CONFIRMED_ONLY`로 검수하던 중, 같은 인물의 PROFILE·ITEM·STATUS 후보가 섞이면 STATUS 문맥 조회에서 `SETTING_CANDIDATE_COMPARISON_STALE`가 발생했다. 재시도 Job은 성공했지만 후보 다섯 개는 `PENDING`으로 남았다.

그룹 입력 hash가 원문 순서 대신 이미 배정된 비교 batch의 순서까지 반영하는 것이 원인이었다. FactType별로 비교하는 동안 배정 순서가 바뀌면 내용·대상·근거가 그대로인데도 다른 입력으로 판단했다. 재시도 역시 초기화 전의 배정 순서로 hash를 만들고 초기화 뒤 비교하므로 새 Job이 처리할 입력이 없다고 오인했다. LLM의 판단 실패나 원문 추출 실패가 아니다.

입력 hash만 배정 이전의 원문 순서로 고정했다. 실제 비교·확정 순서, snapshot·근거·대상·후보 값 변경 검사와 오래된 Job 결과 차단은 유지한다. 정상 기존 Job은 최초 claim 때 전원 미배정 상태였으므로 같은 원문 hash와 호환되며 DB migration은 필요 없다. 이미 잘못 생성되어 대기 중인 후보는 정상 UI 재비교나 동일 인물 재연결로 새 비교 Job을 만든다. 데이터를 강제로 완료하거나 후보를 삭제하지 않는다.

배정 전후·초기화 전후 입력 동일성, 실제 값/대상/근거/후보 집합 변경의 무효화, 혼합 FactType의 claim→문맥 조회→완료 회귀를 추가했다. 수정 전 두 회귀에서 실패를 재현했고 수정 후 관련 49개 테스트와 bootJar가 통과했다. `CharacterFact*`·`SettingCandidate*`로 확장한 26개 클래스 406개 회귀도 실패·건너뜀 없이 통과했다. Java만 재시작한 후 기존 후보를 UI에서 같은 인물에 다시 연결하여 다섯 개 모두 `COMPLETED`로 복구되고 네 개 확정·중복 한 개 제외로 검수를 마치는 것도 실제 PostgreSQL에서 확인했다.

## 연결 확인을 내용 수정으로 오인한 현재값 보호

같은 로컬 검수에서 5화 검토가 완료되어도 정신/전투지수 UPDATE와 부상 REMOVE가 현재값에 적용되지 않는 현상을 확인했다. 이전 2·4화의 후보를 기존 인물에 연결한 작업이 `user_modified=true`를 남겼고, 현재값 보호가 이를 실제 내용 수정과 구분하지 못해 후행 5화의 제안까지 이력으로 돌렸다. 캐릭터 이름을 바꾼 것이 원인은 아니었다.

V73은 nullable `user_content_modified`를 추가한다. 기존 행은 NULL로 보존한 뒤 신규 INSERT에만 false 기본값을 지정하여 기존 Python Worker의 컬럼 생략 INSERT와 호환한다. Java 생성자도 false로 시작하고 설정 이름/값 편집 경로에서 true를 기록한다. 대상 연결과 현재값/이력 선택은 기존 `user_modified`만 기록한다. 아직 수정하지 않았던 기존 후보(NULL·`user_modified=false`)의 첫 연결은 내용 수정 여부를 false로 초기화하고, 이미 수정된 기존 후보(NULL·true)는 추정하지 않고 계속 보호한다. 실제 수동 Fact, 내용 수정, 출처 불명, 동일·후행 회차, 제거된 설정 보호는 완화하지 않는다.

앞 회차에서 대상만 연결한 설정은 후행 회차의 검증된 UPDATE·REMOVE를 허용하고, 실제 내용 수정 및 기존 NULL 행은 계속 보호하는 단건·그룹 회귀를 추가했다. 독립 PostgreSQL에서 V1~V73/JPA validate와 기존 NULL·새 Worker INSERT false 기본값도 확인했다.

최종 관련 회귀는 `CharacterFact*`, `SettingCandidate*`, `ManualCharacterReviewHistoryIntegrationTest`, `AutomaticAnalysisIntegrationTest`의 28개 클래스 552개가 모두 통과했고 실패·건너뜀은 0개다. 별도 PostgreSQL migration 검증 2개와 bootJar도 통과했다. 로컬 Java만 재시작해 V73 성공 및 health UP을 확인했고 기존 후보와 확정 이력은 변경하지 않았다.

마지막 검토에서 미수정 legacy 후보의 첫 연결 경계도 보강했다. 해당 Entity와 수동 현재값 보호의 95개 테스트를 다시 실행해 모두 통과했고 bootJar·로컬 재기동을 완료했다. 이미 `user_modified=true`인 기존 NULL 행의 보호는 그대로다.

이미 UI에서 확정한 5화 데이터는 이 수정으로 소급 재적용하지 않는다. 검수는 1~5화 모두 `MANUAL + CONFIRMED_ONLY`로 종료되어 86개 중 75개 확정·11개 제외·대기 0개이며, 5화의 명시적인 출혈 이력 저장은 정상이다. 다만 수정 이전에 확정한 정신/전투지수/오른발 부상 세 항목은 보호 판단에 따른 이력으로 남아 현재값이 유지된 상태다. 원본과 확정 이력을 보존하며 강제 DB 수정이나 전체 재분석으로 덮지 않았다.


## 같은 회차의 표시된 최종 결과 확정 (2026-10-03)

단일 회차 `MANUAL + CONFIRMED_ONLY`의 수정·제외를 작가의 최종 판단으로 존중한다. 제외/이력으로 바꾼 A에 B의 AI 제안이 의존했더라도 B의 표시 문장은 유지한다. 작가는 보이는 최종 문장을 승인하며 B에서 문장을 빼려면 B를 직접 수정한다. 같은 회차 안에서 AI가 다시 병합 문장을 만들거나 재확인을 반복하지 않는다.

그룹 요청은 `acceptDisplayedResults=true`, 후보별 `expectedUpdatedAt`, 기존 `applicationMode`·snapshot version을 보낸다. 수정 초안에는 `applyEditedValue=true`를 포함한다. 서버는 동일 원본 Job의 완료된 직접 검토인지, 요청이 현재 전체 미확정 그룹인지 먼저 확인한다. 후보 시각·원문 버전·실제 snapshot·대상·schema를 검사하고, 기존 항목별 최신값/직접 수정/삭제 보호를 재사용한다. 제안의 외부 후보 의존 참조와 직접 검토로 우회할 수 없는 실패는 거절한다.

이 경로만 같은 그룹 내부 AI 입력 hash/revision 변화와 선행 후보 제외·이력 의존성으로 재비교하지 않는다. 저장 직전의 실제 상태를 기준으로 STATUS 제거 대상이 이미 없으면 no-op으로 처리하되, 허용 타입·키·중복 검사는 유지한다. 수정하지 않은 제안은 AI의 최종 값을, 수정한 초안은 작가의 최종 값을 저장한다. 같은 확정 재전송은 기존 결정 hash로 멱등 처리한다.

캐릭터 연결 변경, 여러 회차 그룹, 자동 반영의 의존성 정책은 별도 경로로 유지한다. 동명 인물이 외부에서 새로 생성된 경우 조용히 연결하지 않고 충돌을 반환한다. 기존 후행 현재값이 있으면 현재 반영 선택도 이력 저장으로 보호될 수 있다. 이번 계약 추가에는 V72의 기존 nullable 초안 컬럼을 재사용해 별도 migration이 없다.

검증: 관련 Java 580개 통과 후 실패 우회 방지 1개를 추가하고 수동 검토·현재값 보호 91개를 재검증했다(고유 581개). 단일 후보 수정·제외, 선행 후보 이력/제외 뒤 MERGE 문장 보존, 없는 상태 제거, 새 캐릭터 단일 생성, 동시 후보/현재값 변경·원문 교체·다른 Job·진행 중/실패 우회 차단, 멱등 확정이 포함된다. 실제 브라우저와 별도 H2 Spring 서버에서도 수정·제외·새로고침·확정을 확인한다.

테스트 실행 주의: 장시간 켜 둔 HTTP fixture와 일반 `test` 태스크를 동시에 실행하면 공통 `build/test-results/test`의 임시 binary 파일이 다른 실행에서 지워질 수 있다. 이번 브라우저 HTTP 검증 자체는 성공했지만 fixture 종료 시 보고서 생성이 `NoSuchFileException`으로 실패했다. fixture를 종료한 뒤 관련 회귀를 독립 실행해 최종 결과를 다시 만들었다. 향후 동시에 실행해야 한다면 별도 Gradle Test task/결과 디렉터리를 사용한다.
