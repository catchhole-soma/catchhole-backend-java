# 제품 사용 지표의 영속 집계와 Grafana 표시

## 목적과 합의한 요구

GA4 유입·전환과 별도로, 회원 기준 실제 제품 사용량을 서버에서 집계하고 기존 Prometheus → Grafana 경로로 보여 준다.

사용자가 선택한 기준:
1. 분석을 요청한 회원이 아니라 **결과가 준비된 회원**을 센다. 1일·7일·30일 및 이번 달을 표시한다.
2. 반복 분석은 **회원의 첫 완료 이후 추가로 완료한 요청 수**다. 동일 원고 재분석에 한정하지 않는다.
3. 작품 삭제와 회원 탈퇴 후에도 과거 합계를 유지한다. 삭제 후 식별 가능한 원본 기록을 통계 보존 명목으로 남기지 않는다.
4. 작품 생성 수를 현재 보유 작품 수와 구분해 제공한다.

## Approaches

- 기존 현재 DB snapshot 확장: 변경이 작지만 작품·회원 삭제로 과거 수치가 감소한다. 사용자가 보존 요구를 선택했으므로 제외한다.
- **서비스 DB에 영속 집계를 저장하고 기존 Prometheus로 제공**: 중복 방지와 삭제 처리가 필요하지만 재시작·삭제와 무관한 통계를 제공할 수 있다. 사용자가 선택한 방향이다.
- Grafana에서 운영 DB 직접 조회: 연결과 DB 접근 권한이 추가되고 원본 삭제 문제도 해결하지 못한다. 기존 수집 경로를 재사용하므로 채택하지 않는다.

새 공개 API, 새로운 외부 분석 도구, Grafana DB 계정은 만들지 않는다. GA User-ID, 프런트 이벤트, #423/#425/#426 상태는 변경하지 않는다.

## 작성자가 제안한 세부 기준

다음은 사용자에게 아직 별도로 확인받지 않은 구현 제안이며, 최종 확인 대상이다.

### 분석 범위

기존 GA 첫 분석의 제품 의미에 맞춰 회차·설정집의 `SETTING_EXTRACTION`을 센다. 오류 검사, 내부 후보 비교·재비교, 채팅은 제외한다. 기존 요청 기준 7일 지표는 기존 정의를 유지하고 새 완료 지표와 이름을 구분한다.

한 공개 요청의 모든 대상이 준비되어야 요청 1건이다. 회차 10개를 한 번에 요청해도 1건, 설정집 1개 분석도 1건이다. 실패·취소는 완료가 아니며 사용자 재시도와 lease 회수는 원래 요청의 완료를 추가로 늘리지 않는다. 별도로 새 분석을 요청해 완료하면 반복 분석 1건이다.

완료 판정은 결과 준비 로직과 일치해야 한다.
- 대상의 최신 유효 시도가 `SUCCEEDED`, `result_ready_at` 존재, 결과가 `success` 또는 `partial_success`.
- ordered 실행은 `SEALED`, 자동 검토는 자동 반영 완료까지 확인한다.
- 모든 대상의 요청 ID·작품·회원·최초 접수 시각·대상 수가 일치한다.
- 회차와 설정집 source를 구분하여 NULL episode ID로 서로 다른 대상을 합치지 않는다.
- 완료 시각은 모든 대상이 준비된 시각의 최댓값이다. 수집기가 발견한 시각으로 바꾸지 않는다.
- 한때 위 조건을 만족한 완료 사실은 이후 원문 변경으로 journal이 INVALIDATED가 되어도 취소하지 않는다.

### 날짜와 화면

한국 시간의 달력 날짜로 집계한다.
- 1일: 오늘 00:00부터 현재. 화면 이름은 `오늘 분석한 회원`.
- 7일: 오늘을 포함한 최근 7개 날짜.
- 30일: 오늘을 포함한 최근 30개 날짜.
- 이번 달: 이번 달 1일 00:00부터 현재. 30일 수치와 별도다.

자정과 월 경계를 테스트한다. 기존 24시간 요청 지표의 이동 구간은 바꾸지 않는다. Grafana 시간 선택은 새 Stat의 집계 창을 바꾸지 않는다고 설명한다.

운영 현황의 기존 카드를 보존하고, 제품 사용 영역에 완료 회원 4개 Stat과 오늘/이번 달 완료 요청·반복 완료·작품 생성 수를 제공한다. 별도 제품 사용 상세 대시보드에서 일별 추이와 최근 12개월의 월별 회원·완료·반복·작품 생성 표를 제공한다. 이전 달 합계는 DB에서 보존하며 Prometheus 보존 기간이 지나도 다시 읽을 수 있다. 날짜/월 label만 제한된 범위로 내보내며 회원·작품·요청 식별값을 넣지 않는다.

### 수집 시작과 과거 이력

배포 시 기록한 단일 시작 시각을 DB에 보존한다. 새 지표를 과거 전체에 대한 완전한 소급 통계라고 표시하지 않는다.

시작 시각은 migration 실행 시각으로 자동 확정하지 않는다. 기존 API writer를 중단하고 새 버전만 쓰는 것을 확인하는 전환 순서를 사용한다. 최초 새 API가 migration 후, 요청 수락 전에 초기화 트랜잭션으로 시작 시각을 확정한다. 현재 단일 API의 교체 배포가 이 순서를 만족하는지 운영 반영 전에 확인한다. 여러 API의 rolling 전환에서는 구버전 writer가 살아 있는 동안 활성화하지 않으며, 전환을 완료한 뒤 일관된 시작점을 확정한다. 한번 시작된 시각은 재배포·재시작 때 바꾸지 않는다. 전환 중 구버전 쓰기가 없음을 검증할 수 없으면 활성화와 완료 보고를 보류한다.

- 작품 생성 합계는 집계 시작 이후 생성분부터 기록한다.
- 분석 완료 합계는 집계 시작 이후 **최초 접수한 요청**부터 기록한다. 배포 전 이미 완료된 요청을 재시도했다고 새 사용으로 세지 않는다.
- 배포 전 요청은 가능한 범위에서 회원의 과거 완료 여부 판정에만 사용하며, 새 기간 합계에 섞지 않는다.
- 기존 회원에게 과거 완료가 확인되면 이후 완료를 반복으로 분류한다.
- 배포 이후 가입한 회원의 첫 완료는 첫 사용으로 분류한다.
- 기존 회원에게 과거 완료 증거가 없으면 첫 관측을 `과거 이력 부족`으로 분류한다. 이후 완료는 반복이다. 삭제된 기록을 없었다고 추정하지 않는다.
- 늦게 발견된 더 이른 완료는 첫 완료의 날짜를 바로잡는다. 월·일별 첫/반복/분류 불명 합계도 함께 보정한다.
- 첫 달과 관측이 7일·30일에 못 미치는 구간에는 `수집 시작 이후`를 표시한다. 반복 분류 불명이 있으면 확정 반복 건수와 불명 건수를 따로 보여 주고 완전한 반복 사용률로 표현하지 않는다.

## 저장 책임

구체적인 클래스·컬럼 이름은 구현자가 정하되 책임은 분리한다. 모든 변경은 Flyway 신규 migration에 추가하고 JPA 매핑/테스트 schema와 맞춘다.

1. **집계 상태 한 행**: 수집 시작 시각, 성공 시각/진행 정보와 DB 수준 직렬화 잠금. 다중 API에서 중복 처리와 삭제 경합을 막는다.
2. **처리한 요청의 receipt**: 요청 ID, 소유 회원/작품, 완료 시각과 필요한 분류. 요청 ID unique로 재발견·재시도·재시작 중복을 막는다. 원문·이메일·이름·분석 결과를 저장하지 않는다. 작품 파기 시 해당 receipt도 지운다.
   **작품 생성 기록**은 작품 ID unique, 회원 ID, 생성 날짜, 처리 여부만 저장한다. Work 생성과 같은 트랜잭션으로 삽입하고 집계기가 뒤에서 합계에 반영한다. 작품 파기 전에 미처리분을 정산한 뒤 함께 삭제한다.
3. **현재 회원의 집계 보조 기록**: 과거 완료 판정, 최초 관측 완료 시각, 분석한 날짜 집합. 작품 삭제 후에도 동일 회원의 다음 완료를 반복으로 판정하기 위한 계정 단위 요약이다. 작품 ID/제목·원문은 보관하지 않으며 회원 탈퇴 시 모두 삭제한다.
4. **날짜·월 합계**: 날짜 또는 월, 분석 회원 수, 완료 요청 수, 확정 반복 요청 수, 분류 불명 수, 작품 생성 수. 회원·작품·요청 식별값이나 개별 시각 없이 숫자만 영속 보존한다.

집계 테이블의 단순 ID 값이 business 행의 FK lock을 잡아 역순 잠금을 만들지 않도록 설계한다. FK 없이 관리하는 보조 기록은 생성·파기를 같은 직렬화 경계에서 처리하고 orphan 검증을 넣는다. 스키마 선택은 실제 PostgreSQL 경합 테스트로 확인한다.

### 삭제 후에도 서로 다른 회원 수를 보존하는 방법

일별 회원 수를 더해서 월간 회원 수를 만들지 않는다. 같은 회원은 각 기간에 한 번만 센다.

등록된 회원에게만 날짜별 활동 여부를 저장한다. 새 완료 날짜 D가 들어오면 이 회원의 기존 활동 날짜를 확인하고, D부터 D+29까지 각 기준 날짜에서 1일·7일·30일 창에 **새로 포함되는 경우만** 익명 날짜 합계를 1 올린다. 같은 달의 첫 활동일 때만 월별 회원 합계를 올린다. 같은 날 여러 요청·늦게 도착한 과거 날짜도 중복되지 않는다.

미래 날짜 행은 이미 발생한 활동의 유효기간을 예약한 값이며, 해당 날짜가 오기 전에는 화면이나 과거 통계로 노출하지 않는다. 이 방식으로 탈퇴 때 회원별 날짜 기록을 전부 지워도 과거와 향후 만료 구간의 합계를 재계산하거나 개인 식별자를 보존할 필요가 없다.

작품 삭제 시 회원 단위 최초 완료·활동 날짜 요약은 계정이 살아 있는 동안 유지한다. 작품 연결 기록은 지운다. 탈퇴 완료 시에는 회원 연결 기록을 모두 지우고 날짜·월 합계만 남긴다. 재가입은 새 회원으로 센다.

## 수집과 삭제 흐름

기존 60초 서비스 지표 수집 주기를 활용하되, 영속 갱신과 읽기 전용 캐시 조회의 책임을 구분한다. scrape에서는 DB에 접근하지 않는다.

완료 발견:
1. 기존 결과 준비 관측이 후속 비교/자동 반영을 확인한다.
2. 집계기가 완료 요청을 발견하고 집계 상태 잠금 안에서 receipt 여부를 검사한다.
3. receipt 삽입, 회원 요약/활동 날짜, 날짜·월 합계의 갱신을 **한 DB 트랜잭션**으로 커밋한다.
4. 실패하면 모두 rollback하고 다음 실행에 다시 처리한다. 진행 위치를 먼저 전진시키지 않는다.
5. 지연된 관측과 새/동일 Job 재시도를 놓치지 않도록 미처리 요청을 찾는다. 단순 created_at watermark만 사용하지 않는다.

원문 변경·원문 근거 파기:
- 완료된 SEALED Job도 원문 수정 후 INVALIDATED가 될 수 있어 polling만으로는 충분하지 않다.
- `AnalysisRunStateServiceImpl`의 회차 변경·원문 파기 진입점에서 무효화 전에 해당 요청의 준비 상태를 정산한다. 후속 비교가 이미 끝났으나 비동기 tracker가 아직 실행되지 않은 경우도 같은 준비 판정으로 확인한다.
- 기존 source 무효화와 최종 정산을 같은 트랜잭션으로 커밋한다. 실패하면 무효화만 먼저 커밋하지 않는다.
- 이미 완료로 저장된 요청은 무효화 후에도 receipt로 재집계하지 않는다. 완료 조건에 도달하지 못한 요청은 세지 않는다.

작품 생성:
- 실제 Work 생성과 같은 트랜잭션에서 최소 생성 기록만 삽입한다. 기간 조회·회원 중복 제거·합계 계산을 요청 경로에서 실행하지 않는다.
- 집계기가 기록을 읽고 날짜·월 합계 증가와 처리 완료를 같은 트랜잭션에 저장한다. 복잡한 집계의 timeout/오류는 생성된 작품을 취소하지 않고 재처리한다.
- 생성 rollback, 삭제 재시도, 서비스 재시작으로 중복되거나 누락되지 않는다.
- 집계 시작 이전 작품은 migration에서 임의로 소급 합계에 넣지 않는다.
- 최소 기록을 저장하는 DB 쓰기 자체가 실패하면 Work 생성도 rollback한다. 이미 성공한 생성에 대해서만 정확한 기록을 약속하기 위한 원자성이다.

작품 파기:
- 영구 파기 직전에 해당 작품의 준비된 결과를 최종 정산한다.
- 아직 비동기 관측되지 않은 terminal Job의 비교/자동 반영 결과도 확인한다.
- 진행 중 요청을 완료로 만들거나 분석을 다시 실행하지 않는다.
- Job 관측과 물리 삭제가 경합해 완료가 유실되지 않도록 대상 Job 잠금을 먼저 확보한 뒤 집계 직렬화 잠금을 획득한다.
- 최종 정산, 해당 작품 receipt 삭제, 원본 DB 파기는 한 트랜잭션이다. S3 삭제 완료와 별개로 DB 실패 시 기존 재시도 정책을 유지한다.
- 정산 실패 시 삭제를 성공으로 처리하거나 미집계 식별 기록을 따로 남기지 않는다. 기존 DB 파기 실패·재시도 경로로 지연시키고 운영 진단에서 구분한다.

회원 파기:
- 기존 작품 파기가 먼저 완료된 뒤 회원 요약/활동 날짜를 삭제하고 회원을 삭제한다.
- 익명 날짜·월 합계는 감소시키지 않는다.
- PURGING 전환 자체를 과거 사용량 취소로 해석하지 않는다.

잠금 순서는 기존 Member → Work → Job → 집계 상태 순서를 보존한다. polling 집계는 집계 상태 잠금만 보유하고 실제 Member/Work/Job의 잠금 또는 FK 잠금을 요청하지 않는다. 집계 잠금에서 비즈니스 행 잠금으로 역행하지 않는다. 기존 결과 준비 tracker는 business lock을 가진 상태에서 새 REQUIRES_NEW 집계 트랜잭션을 기다리지 않는다. 무효화·파기의 준비 판정은 이미 확보한 Job 잠금과 현재 트랜잭션을 사용한다. 구체적 호출 배치는 구현 전 계획과 PostgreSQL 동시성 테스트로 고정한다.

## Prometheus와 Grafana

- 기존 `catchhole_service_*` 현재 상태 지표와 요청 지표를 보존한다.
- 새 영속 제품 지표는 별도 이름/설명으로 완료 기준임을 드러낸다.
- 유한한 period/window와 최근 날짜/월만 label로 내보낸다. 인스턴스 간 합산하지 않고 최신 정상 snapshot을 선택한다.
- 시작 전, 조회 실패, 180초 이상 갱신 정체는 정상 0으로 채우지 않는다.
- 영속 수집 실패와 읽기 snapshot 성공을 구분한다. 읽기만 성공한 오래된 합계를 정상 최신으로 표시하지 않는다.
- DB에는 전체 월 합계를 보존한다. 최근 12개월을 기본 노출하고 더 오래된 기간 조회 확장은 이번 범위에서 제외한다.
- 운영 대시보드와 datasource UID를 보존한다. 기존 overview 변경은 #432 최종 JSON 또는 live export와 맞춰 패널을 잃지 않게 한다.
- 새 상세 대시보드는 같은 datasource를 사용한다. API 배포 뒤 새 시리즈 수집을 확인하고 JSON을 수동 가져온다.
- 실제 운영 반영 전에 현재 JSON을 백업한다. 로그인 화면에서는 사용자가 직접 로그인하도록 요청한다.

## 검증과 완료 조건

- baseline: 기존 ServiceUsage 28개 테스트 통과. PostgreSQL 4개 포함, skip 0.
- 회원 1명의 같은 날/여러 날/여러 작품 완료가 DAU·WAU·30일·달력 월에 정확히 한 번씩 반영되는지 검증.
- 여러 회차와 설정집, 성공/부분 성공/실패/취소, 자동 반영 대기/ordered 미봉인, 내부 후속 작업 제외.
- 새 Job 재시도·동일 Job 재시도·lease 회수·중복 스케줄·재시작·다중 인스턴스 멱등성.
- 첫 완료 뒤 반복, 기존 회원 과거 이력 부족, 늦게 관측된 더 이른 완료의 일·월별 분류 보정.
- 자정·월말·연말, 시작 전 접수, 시작 후 접수, 관측 기간 부족.
- 생성 rollback과 두 인스턴스 경합.
- 구버전 writer 종료 전후의 최초 활성화 경계, 재시작 시 시작 시각 유지, 생성 기록 삽입 실패와 비동기 합계 실패의 서로 다른 동작.
- 완료 직후 작품 삭제, 대기 중 관측과 삭제 경합, 삭제 후 다른 작품 완료, 회원 탈퇴 후 모든 식별 기록 제거 및 합계 유지.
- 완료 직후 60초 이내 원문 수정/파기로 SEALED → INVALIDATED가 되는 실제 경계와, 아직 준비되지 않은 실행의 무효화 제외.
- 탈퇴 전후 며칠이 지나도 7/30일 창의 만료가 정확한지 확인.
- Flyway 빈 PostgreSQL 전체 migration 및 JPA validate, 필요한 H2 경계 테스트.
- 전체 Gradle 테스트/bootJar, 모든 dashboard PromQL 문법 및 freshness/NaN/중복 관측 fixture.
- 운영 배포 이후 새 metric 수집·Grafana 패널 표시를 확인한다. 실제 배포/로그인 등 외부 단계가 남으면 완료라고 표현하지 않는다.

## 범위와 남은 결정

새 저장 구조, 분석 완료 수집, 작품/회원 파기, Grafana 화면까지 영향을 주므로 작은 패널 수정이 아닌 하나의 기능 작업이다. 사용자는 위 세부 기준과 화면 범위를 최종 확인한다. 구현자가 클래스 배치·SQL 배치 크기·인덱스·조회 최적화·패널 상세 배치를 선택하되 도메인 정책을 바꾸지 않는다. 테스트로 정확성과 DB 잠금 순서를 먼저 확인한다.
