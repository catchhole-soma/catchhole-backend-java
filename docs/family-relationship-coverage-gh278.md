# 가족 관계 미지원 설정 진단 — GH278

[#278](https://github.com/catchhole-soma/catchhole-backend-java/issues/278)은 현재 설정의 명시적 가족 관계 표현을 보완한다. 기존 추출 프롬프트, LLM 호출, Fact 저장 모델과 관계 검토 API는 유지한다.

## 진단 기준과 실제 입력

2026-10-21 운영에서 활성 작품의 현재 프로필과 PROFILE provenance를 읽기 전용 REPEATABLE READ 트랜잭션으로 조회했다. 원문 근거와 과거 Fact 전체는 가져오지 않았다. 진단 입력은 저장소 밖 권한 0600 파일로 보관하며 이 문서와 테스트에는 실제 이름·설정·작품 식별자를 넣지 않는다.

독립 실행기에서 운영과 동일한 `CharacterSnapshotAccessor.read`와 `ExplicitFamilyRelationshipParser.parse`를 사용했다. Spring이나 스케줄러를 시작하지 않고, DB를 수정하거나 모델을 호출하지 않았다. provenance의 타입·캐릭터·factKey를 검증하고, 현재 snapshot에서 사라진 슬롯은 제외했다. 내부 envelope 이전의 값은 실제 코드처럼 마지막 sourceOrder의 Fact 표시값과 현재 valueJson을 함께 사용했다.

| 기준 | 결과 |
| --- | ---: |
| 진단 시점 활성 작품 | 315 |
| 활성 인물 | 454 |
| 현재 PROFILE 입력 슬롯 | 1,587 |
| 가족 표현이 감지된 슬롯 | 148 |
| 기존 규칙이 명제를 만든 슬롯 | 70 |
| 저장된 미지원 슬롯 / 재현한 미지원 슬롯 | 78 / 78 |
| 작품별 미지원 수 불일치 | 0 |
| 출처 20개 초과로 미지원인 슬롯 | 0 |

이전 백필 당시 활성 작품은 312개였고 이번 진단은 그 이후의 snapshot이다. 미지원 78건은 이번 snapshot에서 작품별로 일치했다. 78건 모두 파서가 관계 명제를 만들지 못했으며 `UNSUPPORTED_FAMILY_SYNTAX`가 기록됐다. 이 중 1건은 표시값과 구조화 값이 달라 `CURRENT_VALUE_CONFLICT`도 함께 있었다. 입력 길이·명제 수·출처 수 상한이 실제 원인은 아니었다.

## 변경 후 같은 입력의 결과

기존 미지원 78개 슬롯 중 26개에서 34개의 명제를 읽었다. 13개 슬롯의 17개 명제는 ASSERTED, 나머지 13개 슬롯의 17개 명제는 UNCERTAIN이다. 명확한 문법 누락으로 분류한 19개는 모두 읽으며, 혼합 문장 7개는 읽힌 관계도 검토 대상으로만 남긴다. 이 26개 슬롯은 11개 작품에 있다.

원래 78개 중 52개는 계속 미지원이다. 상대 정보가 없거나 가문·비유·지원 밖 친족인 항목을 수치 감소를 위해 인물 관계로 만들지 않았다. 앞 형제 호칭의 기존 불확실성 정책도 유지한다.

기존에 파싱되던 70개 슬롯도 함께 대조했다. 68개는 명제·방향·호칭·단정·시점 결과가 같고, 2개는 오인식을 수정했다. 하나는 `민준과 서연`을 한 사람으로 보던 결과를 두 상대의 관계로 나눈 경우이고, 다른 하나는 `청연세가` 같은 집단을 부모 인물로 보던 결과를 제외한 경우다. 따라서 남은 전체 미지원 수에는 원래 52개에 기존 오인식 1개가 추가된다.

새로 지원한 역할 어휘로 기존 집계 밖의 `동해박가의 서녀` 형태도 감지된다. 이 예시는 가상 이름으로 바꾼 것으로, `~가`가 사람인지 집단인지 단정하지 않고 검토한다. 이 추가 감지 역시 기존 78건 개선 수와 분리한다. 파서는 인명 인식 모델이 아니며 모든 자유 서술에 대한 정답률을 측정한 것은 아니다.

부모·자녀 명사구 끝의 정확한 소유자 이름을 가계도 호칭 조회에도 전달한다. 추가 인물 조회 없이 기존 활성 인물 결과를 재사용하여 `딸`이 중립 `자녀`로 바뀌는 표시 누락을 막는다.

## 기존 데이터 적용 경계

동일한 비공개 snapshot에 변경 전·후 파서를 적용하여 결과를 대조한다. 기존 70개 파싱 슬롯의 명제·상대·방향·시점·단정 여부가 변했는지 별도로 검사한다. 원래 프로필과 출처는 수정하지 않는다.

코드 배포만으로 이미 완료된 작품의 입력 버전이 증가하지는 않는다. 진단 snapshot에서 결과가 바뀐 작품은 11개이며 대상 식별자는 비공개 manifest에 보관했다. 운영 반영 시에는 해당 작품의 현재 입력을 다시 확인하고, 배포 SHA를 확인한 뒤 기존 작품별 관계 처리 요청으로 재처리한다. 기존 제외·수정·확정·철회 결정 보존 및 관계 처리 완료를 확인해야 한다. 이 문서의 파서 재실행은 운영 재처리 완료 기록이 아니다.

## 실행 검증

2026-10-21 JDK 21에서 `env -u DOCKER_HOST ./gradlew test bootJar --console=plain`을 실행했다. 전체 3,736건 중 3,500건 통과, 기존 조건부 skip 236건, 실패·오류 0건이며 `bootJar`도 성공했다.

합성 회귀는 명시적 역할·수식어·소유자 이름·복수 상대와 부정·비유·과거 범위, 가문·상황문 오연결 방지를 검사한다. H2 및 격리 PostgreSQL 통합 테스트에서는 새 복문의 등록 관계·미등록 자녀 표시, 원래 근거 보존, 재처리 중복 방지, 혼합 문장 검토와 가계도 제외, 정확한 소유자 접미사의 딸 호칭을 검증했다. 기존 사용자 수정·제외·확정·철회 보존 회귀도 함께 통과했다.

실제 입력 재실행에서는 명확한 문법 누락 19개를 모두 읽었고, 나머지 수동 분류 범주에서 새 ASSERTED 명제를 생성하지 않았음을 확인했다. 실데이터 진단, 합성 DB 통합 테스트, 운영 적용을 서로 다른 검증 범위로 기록한다.
