## 1. 데이터 보호 목표와 판단 기준

| 항목 | 운영 목표 | 판단 기준과 한계 |
| --- | --- | --- |
| RPO: 허용 데이터 손실 시간 | **15분 이내** | 실제 사용자 작품·설정이므로 하루 단위 손실을 기준으로 삼지 않는다. RDS의 5분 간격 로그 업로드를 바탕으로 정한 초기 목표이며, 15분 손실이 항상 발생하거나 AWS가 이를 보장한다는 뜻은 아니다. |

| 삭제 보호 | **활성 유지** | 운영 DB 인스턴스의 실수에 의한 삭제를 막는다. SQL `DELETE`·`DROP`이나 백업 자체의 삭제까지 막는 기능은 아니다. |

### 1.1 RPO의 적용 범위와 확인 방법

RPO 15분은 운영 DB를 잃었을 때 복구하지 못하는 **최근 커밋 데이터의 시간 범위**를 최대 15분으로 제한하려는 목표다. 데이터의 15%나 백업 보존 기간을 뜻하지 않는다.

AWS는 RDS DB 인스턴스의 트랜잭션 로그를 S3에 **5분마다 업로드**한다고 명시한다. PostgreSQL의 변경 기록인 WAL을 15분 RPO에 맞춰 사용자가 14분마다 전송하도록 설정하는 구조는 아니다. 평상시 백업 상태는 다음 차이를 관찰한다. [AWS 시점 복구 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

```text
관측 시점의 복원 지연 = 확인 시각 - LatestRestorableTime
관측 기준: 15분 이내
```

값이 없거나 갱신이 멈추면 정상으로 간주하지 않는다. 한 번의 정상 조회나 스냅샷 개수만으로 지속적인 RPO 충족·실제 복구 성공을 확정하지 않는다. 복원 지연의 수집 주기, 경고·초과 기준, 알림·복구 통지와 최초 대응 절차는 T4에서 정하고 검증한다.

이번 목표는 **서울 리전의 복구 원본과 AWS 관리 기능, API·Worker EC2 및 필요한 외부 의존성을 사용할 수 있는 운영 DB 장애**를 기준으로 한다. 리전 전체 장애, 계정·백업까지 함께 손실되는 사고, 늦게 발견된 SQL 오삭제의 데이터 선별·병합 시간을 동일 목표로 검증한 것은 아니다. DB 시점 복구는 S3 원문·Redis·외부 발송 등의 상태까지 함께 되돌리지 않는다.

### 1.2 RTO의 시작·종료 기준

- 시작: **실제 서비스 중단 시각**. 담당자가 알림을 확인한 시각부터 다시 계산하지 않는다. 정확한 시작을 모르면 마지막 정상·최초 실패 관측 시각을 함께 남긴다.
- 종료: API·Worker가 복원 DB를 사용하고, 대표 작품·설정의 조회·저장 및 대표 Worker 처리 경로를 확인해 서비스 재개를 판단한 시각.
- 밀린 Job 전체의 처리 완료는 종료 조건에 포함하지 않는다. 다만 복원된 과거 Job의 재처리, 외부 부수효과의 중복 가능성을 검토한 뒤 Worker를 재개해야 한다.

다음은 **계획상 시간 예산**이다. AWS 보장, 실측값 또는 현재 확보된 대응 체계로 해석하지 않는다.

| 구간 | 예산 | 세부 작업 예시 | 충족에 필요한 준비·확인 |
| --- | --- | --- | --- |
| 감지·초기 대응 | **15분** | 발생 후 0–3분 감지·발송, 3–8분 담당자 확인, 8–15분 AWS 접속·영향 확인·복원 필요성 판단 | DB 연결 실패를 반영하는 외부 감시, 알림 전달 시험, 1차·2차 담당자와 야간 대응 가능 여부, SSO·조회 권한 |
| DB 복원 | **60분** | 복구 원본·시점·설정 선택 및 요청 10분, AWS 복원 처리 대기 45분, 기본 연결·SQL 확인 5분 | 복원 권한과 사양·네트워크·암호화·파라미터 설정 준비, T5 실제 소요 시간 측정 |
| 연결 전환·서비스 검증 | **30분** | 기본 DB 확인 및 API·Worker 연결 설정 반영·기동 10분, 핵심 기능 점검 15분, 오류·응답 상태 관찰 5분 | 안전한 전환 절차, 대표 데이터·테스트 계정·점검 항목 준비, 장시간 Worker 작업의 측정 |
| 여유 | **15분** | 재로그인·설정 재확인·기동 지연 등 작은 변동 | 장시간 AWS 지연이나 권한 누락을 흡수한다고 가정하지 않음 |

감지는 예를 들어 **1분마다 확인하고 연속 2회 실패하면 알리는 방식**을 T3·T4에서 검토할 수 있다. 현재 적용한 설정은 아니다. 서비스 이상을 먼저 감지하고 콘솔·이벤트로 DB 삭제 여부를 확인한다. RDS 삭제 이벤트는 존재하지만 EventBridge 전달은 best effort이므로 단독 감지 수단으로 15분 대응을 보장하지 않는다. SQL로 일부 데이터가 삭제되어도 연결은 정상일 수 있다. [RDS 이벤트 목록](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_Events.Messages.html), [RDS 이벤트 전달](https://docs.aws.amazon.com/eventbridge/latest/ref/events-ref-rds.html)

**1차·2차 담당자의 실명 배정, 야간 수신·응답 체계와 감지 시간은 미검증**이다. 알림을 받을 사람이 없으면 15분 대응과 전체 RTO 목표가 깨진다. 시간이 지났다는 이유로 원인을 확인하지 않고 복원을 강행하거나 검증을 생략하지 않는다.

DB 복원은 새 인스턴스를 만드는 방식이며, `available` 이후에도 백그라운드 데이터 로딩으로 초기 쿼리가 느릴 수 있다. gp3 30GiB라는 할당량만으로 60분을 계산할 수 없다. 기본 연결 확인과 서비스 성능 확인을 구분한다. [AWS 스냅샷 복원 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_RestoreFromSnapshot.html)

서비스 재개 점검에는 다음을 준비한다.

1. 복원 시점에 존재해야 할 대표 작품·설정과 기준 데이터를 조회한다.
2. 테스트 계정으로 작품·설정을 저장하고 다시 조회한다.
3. API·Worker의 새 DB 연결, 인증, Flyway 이력·JPA/SQLAlchemy 매핑 및 필요한 확장 기능을 확인한다.
4. 대표 Worker 처리 결과와 과거 Job 재실행·외부 부수효과의 중복 가능성을 확인한다.
5. 핵심 요청의 오류·응답 상태를 사전에 정한 정상 기준과 비교한다. 현재 이 문서는 응답 시간 기준을 실측·확정하지 않는다.

T5는 운영 API·Worker·S3 쓰기와 분리된 복원 훈련이다. 위 점검은 격리 환경에서 가능한 범위를 실행하고, 실제 운영 전환·실서비스 외부 호출은 실행한 것으로 기록하지 않는다. T5만으로 감지부터 운영 재개까지 2시간 전체를 입증하지 않는다. 각 구간의 실측과 미측정을 남기고 목표 달성 가능성 또는 절차 개선 필요성을 재평가한다.

## 3. 삭제 보호와 계획 삭제 시 최종 스냅샷 절차

운영 중 삭제 보호는 계속 활성화한다. 최종 스냅샷 생성과 자동 백업 유지는 **DB 삭제 요청 시 각각 선택하는 옵션**이며, 평소 켜 둘 하나의 영구 설정이 아니다. T2에서는 운영 DB 삭제·복원과 삭제 보호 해제를 실행하지 않았다.

운영 DB를 의도적으로 폐기하는 별도 작업에서는 다음 절차를 따른다.

1. 운영 담당자가 삭제 대상·사유, 데이터 보존 요구, 실행자와 검토자, 복구 원본을 기록하고 팀의 삭제 승인을 받는다. 실수 방지용 삭제 보호를 평상시 해제해 두지 않는다.
2. 서비스 이전 또는 종료 상태와 최종 쓰기 중단 여부를 확인한다. 필요한 백업과 복원 가능한 시점, 접근 권한을 먼저 확인한다.
3. 승인된 삭제 시점에만 삭제 보호를 해제하고, 삭제 요청에서 **최종 스냅샷 생성**과 **자동 백업 유지**를 모두 선택한다. 이름·확인 시각·삭제 옵션은 비공개 운영 기록에 남긴다.
4. 삭제 후 최종 스냅샷의 `available` 상태와 보유 자동 백업을 확인한다. 실패하거나 확인되지 않은 상태를 완료로 표시하지 않는다.
5. 이전·폐기 검증 이후 최종 스냅샷의 계속 보관 필요성, 비용과 삭제 담당자를 검토해 별도 정리 결정을 기록한다.

DB가 `failed` 등 일부 상태이면 최종 스냅샷을 만들 수 없다. 이런 경우 임의로 스냅샷 생성을 생략해 계획 삭제를 계속하지 않고, 기존 복구 원본과 별도 사고 대응 결정을 확인한다. 최종·수동 스냅샷은 **자동 백업 7일 정책으로 자동 삭제되지 않는다**. [AWS 삭제 옵션·제약](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_DeleteInstance.html)

유지한 자동 백업에는 인스턴스 삭제 시의 보존 기간이 적용되지만 삭제 후 새 로그가 추가되지는 않는다. 보유 백업의 복원 범위와 만료를 직접 확인하며, 삭제 이후 어느 시점의 데이터까지 계속 보호된다고 가정하지 않는다. 보유 자동 백업과 수동 스냅샷은 보관 비용이 발생할 수 있다. [AWS 자동 백업 보유 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.Retaining.html)

## 4. T4·T5에 전달할 확인 경로와 접근 권한

### 4.1 콘솔에서 직접 확인

[서울 리전 RDS 콘솔](https://ap-northeast-2.console.aws.amazon.com/rds/home?region=ap-northeast-2)에 운영 SSO 계정으로 접속한다. 다른 계정·리전의 빈 목록과 혼동하지 않도록 대상 계정을 먼저 확인한다.

| 목적 | 경로 | 확인할 내용 |
| --- | --- | --- |
| 최근 복원 가능 시점 | 자동 백업 → 현재 리전 → 운영 DB | 가장 빠른/최근 복원 가능 시간, 보존 기간, 백업 상태 |
| 자동 스냅샷 | 스냅샷 → **시스템** 탭, 또는 자동 백업 상세의 시스템 스냅샷 | 생성 시각, `available`·완료 여부, 상세 이벤트 |
| 수동·최종 스냅샷 | 스냅샷 → **수동** 탭 | 수동 백업 목록. 여기가 비어 있다고 자동 백업이 없는 것은 아님 |
| 삭제 보호 | 데이터베이스 → 운영 DB → **구성** | `삭제 방지 활성화됨` |
| 백업 설정 | 데이터베이스 → 운영 DB → **유지 관리 및 백업** | 자동 백업·백업 시간·보존 설정 |
| 삭제 후 유지한 자동 백업 | 자동 백업 → **보유** 탭 | 해당 백업의 상태·복원 범위·만료 |

스냅샷 화면에서는 메타데이터를 확인한다. 작품·설정의 실제 복구 데이터 확인은 T5에서 **격리 복원 DB에 별도 접속**해 수행한다. IntelliJ의 기존 운영 DB 접속이나 자택 IP 허용은 AWS 백업 관리 권한과 다르다.

### 4.2 권한과 책임의 구분

| 수행 주체·목적 | 필요한 권한·준비 | 이번 확인 상태와 후속 책임 |
| --- | --- | --- |
| 현재 운영 SSO 사용자: 수동 백업 확인 | 운영 DB 설정·스냅샷·자동 백업 상세 조회 | **콘솔 조회 성공**. 개별 계정·역할 식별자는 운영 계정에서 확인하고 공개 저장소에 복사하지 않음 |
| 다른 팀원: 같은 경로의 수동 확인 | 해당 팀원에게 할당된 운영 계정·SSO 역할 | 해당 팀원으로 로그인해 보지 않았으므로 동일 권한을 보장하지 않음. 운영 담당자가 필요 시 할당·접근 경로를 안내 |
| T4 구현 담당자: 자동 수집·알림 | 수집 서비스 실행 역할의 RDS 조회 및 선택한 알림 수단의 권한 | 이번 문서에서 실행 역할을 신설·검증하지 않음. T4에서 방식 선택 후 역할·알림 수신자·미응답 대응을 구성·시험 |
| T5 복원 훈련 담당자 | 선택한 복원 API, 종속 생성 권한, 네트워크·암호화 키 사용, 훈련 자원 정리 권한 | **실제 복원 권한 미검증**. T5 시작 전 운영 권한 관리자와 실행 역할·대상·비용·정리 권한 확인 |

조회 작업의 주요 API는 `rds:DescribeDBInstances`, `rds:DescribeDBSnapshots`, `rds:DescribeDBInstanceAutomatedBackups`, 이벤트 확인 시 `rds:DescribeEvents`다. T4는 사람이 쓰는 SSO 세션을 상시 수집기의 자격 증명으로 사용하지 않도록 실행 역할을 별도로 정한다.

T5의 주요 복원 API는 방식에 따라 `rds:RestoreDBInstanceToPointInTime` 또는 `rds:RestoreDBInstanceFromDBSnapshot`이다. 이 두 권한만으로 충분하다는 IAM 정책 예시는 아니며 종속 권한, 리소스 범위, KMS·조직 SCP 등의 제약을 함께 확인해야 한다. 정리 권한은 훈련 리소스에 한정하고 운영 DB 삭제를 권한 시험으로 사용하지 않는다. 조회 성공·복원 버튼 표시만으로 복원 권한을 입증하지 않는다. [RDS 서비스 권한 참조](https://docs.aws.amazon.com/service-authorization/latest/reference/list_rds.html)

### 4.3 재조회용 읽기 전용 CLI 예시

아래는 콘솔 대신 사용할 **재조회 예시**다. 이번 점검에서는 CLI 세션이 만료되어 실행 결과로 사용하지 않았다. 유효한 SSO 세션을 준비하고 두 placeholder를 본인의 운영 값으로 바꾼다. 원본 계정 ID·ARN·접속 주소·비밀값을 출력하지 않도록 필요한 필드만 선택한다.

```bash
TASK_AWS_PROFILE='<운영 SSO 프로파일>'
TASK_RDS_ID='<운영 RDS 식별자>'

date -u '+조회 시작: %Y-%m-%dT%H:%M:%SZ'
aws rds describe-db-instances \
  --profile "$TASK_AWS_PROFILE" --region ap-northeast-2 \
  --db-instance-identifier "$TASK_RDS_ID" \
  --query 'DBInstances[0].{Status:DBInstanceStatus,RetentionDays:BackupRetentionPeriod,BackupWindowUTC:PreferredBackupWindow,LatestRestorableTime:LatestRestorableTime,DeletionProtection:DeletionProtection}' \
  --output json --no-cli-pager
date -u '+조회 종료: %Y-%m-%dT%H:%M:%SZ'

aws rds describe-db-snapshots \
  --profile "$TASK_AWS_PROFILE" --region ap-northeast-2 \
  --db-instance-identifier "$TASK_RDS_ID" --snapshot-type automated \
  --query 'sort_by(DBSnapshots, &SnapshotCreateTime)[].{CreatedAt:SnapshotCreateTime,Status:Status,Type:SnapshotType}' \
  --output json --no-cli-pager
```

조회 실패·대상 없음·`LatestRestorableTime=null`은 정상 지연 0분으로 치환하지 않는다. 확인 시각과 반환 시각을 같은 시간대로 비교한다. 이 명령은 알림을 만들거나 복원을 수행하지 않는다.

## 5. 변경 결과·운영 영향·비용과 완료 범위

| 항목 | 9월 10일 확인값 → 9월 11일 재확인값·결정 | 적용 시점·영향·추가 비용 |
| --- | --- | --- |
| 자동 백업 보존 | 7일 → **7일 유지** | AWS 변경 요청 없음, 보존 연장에 따른 추가 비용 없음 |
| 백업 시간대 | UTC 16:35–17:05 → **유지** | 변경 없음 |
| 삭제 보호 | 활성 → **활성 유지** | 해제·삭제 시험 없음 |
| 복원 지연 확인 | 9월 10일의 과거 관측 → **9월 11일 약 2분 차이 관측** | 자연 갱신된 관측값이며 설정 변경이 아님 |
| 목표·삭제 절차·확인 경로 | T2에서 검토·문서화 | 문서 PR에 기록. AWS 설정의 적용 시각은 해당 없음 |
| 신규 AWS 자원 | **생성 없음** | 이번 작업에서 추가한 상시 자원 비용 없음. 기존 운영·백업 비용이 0이라는 뜻은 아님 |

현재 설정은 선택한 7일 보존·삭제 보호 기준과 일치하고 최근 복원 가능 시점도 조회 시 15분 기준 안에 있으므로 재설정하지 않는다. 설정 미비가 발견되면 변경 전후 값·적용 시각·영향·비용을 별도로 기록한다. T4 알림 수집 비용과 T5 임시 DB·스토리지·보관 비용은 각 작업에서 산정한다.

이번 작업의 AWS 조작은 조회뿐이며 DB 재시작·운영 전환은 실행하지 않았다. 다만 저장소의 현재 `publish-image.yml`은 문서만 바뀌어도 **main push 시 이미지 발행을 시작**하고 후속 배포 조건에 따라 API 배포가 이어질 수 있다. PR 머지는 기존 배포 Workflow의 영향도 함께 검토하며, 이 문서 PR에서 Workflow를 변경하지 않는다.
