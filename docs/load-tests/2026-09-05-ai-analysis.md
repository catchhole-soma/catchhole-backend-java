## 목적과 범위

Mac에서 운영 API에 파일 업로드와 분석을 요청하여 API → S3 → Worker → RDS 결과 저장을 확인한다. 부하 발생기를 EC2에 설치하거나 서비스 코드를 수정하지 않는다. 계정 1개에 서로 다른 테스트 작품 N개를 만들고 각 작품에 회차 1개씩 업로드한다.

같은 작품에 같은 회차를 중복 요청하는 테스트가 아니다. 동시 분석 슬롯·대기열·결과 저장을 확인하는 기본 실험이며, 다계정 인증 격리·누적 장편 작품의 복잡도·대용량 동시 업로드·분석 정확도 평가·장시간 지속 부하는 별도 범위다.

## 단계별 실행 계약

1. 실행 식별자를 만든다. 예: `analysis-20260905-10-run01`. 작품 제목에는 `부하테스트-<실행 식별자>-001`처럼 식별 가능한 접두사를 쓴다.
2. 해당 단계 전용 작품 N개를 만든다. 인증 계정·작품 소유권 검사는 기존 API를 그대로 사용한다.
3. 각 작품에 TXT를 업로드한다. `POST /api/v1/works/{workId}/episodes`의 multipart `metadata`에는 `uploadType=SINGLE_EPISODE`, 승인 입력의 회차 번호(`fixture-004`는 `singleEpisodeNo=4`, `fixture-005`는 `5`)를 사용하고 파일은 `episodeFiles`로 전송한다. `episodeConfirmations`를 섞지 않는다.
4. 작품/회차/업로드 배치 ID를 비공개 실행 기록에 저장한다. 모든 업로드가 정상이어야 분석 접수를 시작한다. 업로드 준비 시간은 별도 측정하며 이번 단계에서 100개 파일을 동시에 업로드한다고 해석하지 않는다.
5. 각 작품에 `POST /api/v1/works/{workId}/analysis-jobs`로 `jobType=SETTING_EXTRACTION`, 해당 `batchId`, 해당 `episodeId`를 전송한다. N개의 요청을 짧은 구간에 보내되 실제 첫/마지막 전송 시각 차이를 기록한다.
6. 각 응답 목록에 Job 한 개가 생성됐는지 확인하고 ID를 보존한다. HTTP 성공은 분석 완료가 아니다. timeout·409·401이 있으면 상태 확인 없이 같은 생성 요청을 재전송하지 않는다.
7. `GET /api/v1/works/{workId}/analysis-jobs/{analysisJobId}`로 상태를 관찰한다. 초기 polling 계획은 Job별 5초 간격이며 실제 간격·오류·관찰 공백을 기록한다. 미완료 10/50/100건이면 약 2/10/20회의 조회/초가 추가되므로 접수 성능 지표와 분리한다.
8. 모든 Job의 최종 상태, 회차 결과 및 캐릭터·세계관 후보 비교 상태를 확인한다. API 응답이나 원문·후보 전문 대신 허용된 상태·시각·건수만 집계한다.
9. 서버 상태와 오류 로그를 함께 검토한 뒤 다음 단계 실행 여부를 결정한다. 10 → 50 → 100을 모두 실행하면 총 160건이며, 각 단계는 새로운 작품을 사용한다.

서버 `LocalDateTime`은 시간대가 없는 값이다. 운영 APP_TIMEZONE을 확인한 뒤 명시적으로 해석하며 Mac UTC timestamp와 그대로 빼지 않는다. polling으로 관측한 완료 시간에는 최대 polling 간격과 네트워크 지연이 추가될 수 있다.

재시도/lease 회수로 시작 시각이 바뀌면 마지막 timestamp만으로 최초 대기 시간과 전체 실행 시간을 복원하지 않는다. 상태 변화 기록으로 구간을 분리하거나 해당 시간 지표를 미측정으로 남긴다. 미완료·실패를 0ms로 넣지 않고 분모·표본 수를 공개한다.

성공 Job 시간 분포의 p95/p99는 원본 시간 표본을 정렬한 nearest-rank 방식(`ceil(p × N)`번째 값)으로 계산할 계획이다. 실패·미완료 건수와 관찰 시간을 반드시 나란히 적는다. 기존 조회 테스트의 k6 percentile과 계산 방식이 같다고 가정하지 않는다. 10건의 p95는 최댓값에 해당하여 안정적인 운영 p95로 해석하지 않는다.

`maximumSampledRunning`은 순차 polling에서 서로 다른 시점에 읽은 Job 상태의 합계다. 같은 순간의 snapshot이 아니며 끝난 Job의 이전 RUNNING과 새 Job의 RUNNING이 함께 계산돼 실제 동시성보다 커질 수도 있다. 따라서 최대 동시성의 하한이라고 부르지 않는다. 재시도·시각 정밀도를 확인한 서버 `[startedAt, completedAt)` 구간의 최대 겹침 수로 별도 검증하고 원래 polling 집계를 보존한다. 타임스탬프가 lease 재시도로 바뀐 경우에는 이 계산도 제한된다. 100건 단계에서 즉시 정확히 50건 실행·50건 대기가 보여야 한다고 가정하지 않는다. 과거 실행기의 `limitations`에 적힌 하한 표현은 이 설명으로 정정한다.

## 성공 판정과 중단

Job `SUCCEEDED`만으로 모든 비교 성공을 단정하지 않는다. 후보 비교 실패가 남아도 회차 Job이 종료될 수 있으므로 비교 실패·진행 중 후보, 토큰 중단과 결과 조회를 별도로 검사한다. 후보가 사용자 검토 대기 상태인 것은 서비스의 정상 흐름이며 자동 확정하지 않는다.

기본 진행 조건은 대상 Job 전부 정상 종료, 기대한 결과 조회 가능, 후보 비교 실패/미완료 없음, 서비스 건강 상태 유지다. 분석 시간의 절대 목표는 아직 미정이며 10건 결과를 기준으로 합의한다. 미완료나 관측 누락을 성공으로 바꾸지 않는다.

중단 및 운영 조치 원칙은 [공통 계획의 진행·중단 기준](README.md#4-진행중단-기준)을 따른다. 실행기 종료는 이미 접수한 분석 취소가 아니며, 관찰용 토큰 만료도 서버 분석을 중지하지 않는다.

- 앞선 실행과 동일하게 모든 보고 토큰에 할인 없는 Terra 표준 텍스트 요율을 적용하면 `(4613675×2 + 481215×12)/1000000 = $15.001930`. 예산 계산용 1달러=1,500원 가정이면 이번 약 **22,503원**, 이전 70건까지 합쳐 누적 약 **39,049원**이다. 실제 공급자 청구액·모델별 할인·캐시 쓰기·장문 요율·세금·수수료를 정산한 값은 아니므로 50,000원의 기술적 hard limit을 보장하지 않는다.
- **요청한 100건 단계의 접수·대기→실행→종료 관측은 완료**했다. 50슬롯에서 초과 요청이 대기한 뒤 소진되는 흐름을 확인했지만, 비교 검증 실패 두 작품 때문에 전체 기능 성공 판정은 실패다. 장시간 지속 부하·다계정·다양한 원문·기존 설정 누적·대용량 동시 업로드·RDS 자원 여유는 별도 실험이다.
- 현재까지 신규 분석 **170건**을 수행했고 추가 분석은 접수하지 않았다. 테스트 작품과 결과는 삭제하지 않고 유지했다. 이후에는 남은 비교 검증 실패 처리와 실제 비용 확인을 먼저 결정하며, 더 큰 부하나 유료 재시도는 새 승인 없이 실행하지 않는다.
