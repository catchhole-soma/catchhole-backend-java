# 운영 API 소규모 읽기 부하 테스트 결과

통합 이슈: [Java #164](https://github.com/catchhole-soma/catchhole-backend-java/issues/164)

기존 임시 기록을 Java 저장소로 이관했다. 원본 집계 JSON과 조회 실행기는 그대로 보존했으며, 이 문서의 링크·공개용 식별자 표기만 정리했다. 이관 과정에서 운영 부하 테스트를 다시 실행하지 않았다.

## 결론

같은 테스트 계정의 작품 목록을 반복 조회하는 1·5·10 VU 단계는 모두 완료했고, 측정 대상 조회 3,589건이 전부 성공했다. 각 단계의 종료 코드는 0이며 임시 기준인 p95 < 1,000ms와 오류율 0%를 충족했다.

종료 후 API EC2의 루트 디스크 사용률이 91%로 확인됐다. 사용자가 SSM에서 태그 없는 미사용 이미지를 정리해 13.56GB를 확보했고, 디스크 사용률은 46%로 내려갔다. 이후 사용자 요청에 따라 이전 Worker·PostgreSQL·테스트 컨테이너와 관련 이미지, 기존 PostgreSQL 데이터 볼륨까지 삭제했다. 최종 API EC2에는 Java·Caddy·Redis 컨테이너만 남았고, 공개 헬스 체크는 `UP`이다.

## 실행 조건

- 실행 위치: 사용자 Mac의 k6 v2.1.0
- 요청 대상: `GET https://api.catchhole.com/api/v1/works`
- 데이터: 작품 1개가 등록된 동일 테스트 계정의 액세스 토큰 공유
- 부하: 가상 사용자 1명 1분 → 5명 2분 → 10명 5분, 단계별 별도 실행
- 각 가상 사용자는 응답을 받은 뒤 1초 대기; 실제 서로 다른 계정 10개를 사용한 테스트는 아님
- 검증: HTTP 200, `success=true`, 비어 있지 않은 `data` 배열
- 실패 시 즉시 중단하고, 단계 시작·실행 중·종료 시 헬스 체크 수행
- 작품·AI 작업 생성, 유료 LLM 호출, 배포 및 운영 설정 변경은 수행하지 않음

## 부하 종료 직후 서버 상태 — 디스크 정리 전

사용자가 API EC2의 SSM 터미널에서 직접 실행해 전달한 출력이다. 출력 시작 시각은 `2026-09-05T06:24:38+00:00`, 한국 시간 15:24:38이다. 최종 부하 종료 약 8분 후부터 확인한 스냅샷으로, 부하 중 최대 사용량을 뜻하지 않는다.

| 대상 | 확인 결과 |
| --- | --- |
| Backend | CPU 0.22%, 메모리 621.5MiB |
| Caddy | CPU 0.03%, 메모리 12.88MiB |
| Redis | CPU 0.46%, 메모리 7.145MiB |
| EC2 메모리 | 총 3.7GiB, 사용 1.3GiB, available 2.4GiB |
| Swap | 총 2.0GiB, 사용 8.9MiB |
| 루트 디스크 | 총 29G, 사용 26G, 가용 2.6G, 사용률 91% |
| Backend 현재 컨테이너 | `status=running restarts=0 oom=false` |

API EC2는 SSH 접속이 차단되어 있고 SSM으로 접근한다. 자동 브라우저 연결 오류로 부하 중 서버 자원을 수집하지 못했다. 화면 제어 입력도 정상 실행을 확인하지 못했으므로 그 시도의 출력은 증거로 사용하지 않았다. 위 서버 수치는 사용자가 SSM에서 정상 실행한 출력만 사용했다.

## 해석의 범위

- 이번 동일 계정·작은 데이터셋의 읽기 시나리오는 임시 기준을 통과했다.
- 이 결과만으로 전체 서비스의 최대 동시 사용자 수나 최대 처리량을 판단할 수 없다.
- 여러 계정·다양한 데이터, 쓰기·업로드·AI 처리, Worker 처리량은 검증하지 않았다.
- 부하 중 CPU·메모리·RDS 지표는 미수집이며, 종료 후 메모리 여유나 재시작 횟수로 이를 대신할 수 없다.
- journald의 테스트 시간대 오류 로그는 아직 별도로 확인하지 않았다.

## 디스크 정리 및 이전 로컬 환경 제거

### 원인 확인

사용자가 `docker system df`, `journalctl --disk-usage`, `du -xhd1 /var /opt`를 실행해 전달한 결과:

- Docker 이미지 75개, 16.72GB 사용, 회수 가능 표시 13.57GB
- Journal 로그 135.6MB, `/var/log` 전체 212MB
- `/var/lib` 17GB, `/opt` 64KB
- 주원인은 로그가 아니라 누적된 Docker 이미지였다.

### 1차 정리: 태그 없는 미사용 이미지

`docker image ls -a --filter dangling=true`로 대상을 확인했다. 첫 `docker image prune` 실행은 삭제 출력과 용량 변화가 없어 정리가 적용되지 않은 것으로 판단했다. 승인 입력이 처리되지 않은 가능성은 있으나 정확한 원인은 확정하지 않았다.

사용자가 `sudo docker image prune --force`를 실행한 결과:

| 항목 | 정리 전 | 1차 정리 후 |
| --- | --- | --- |
| 이미지 수 | 75 | 10 |
| 이미지 사용 공간 | 16.72GB | 3.158GB |
| 루트 디스크 사용률 | 91% | 46% |
| 루트 디스크 가용 공간 | 2.6G | 16G |

Docker가 보고한 확보 공간은 13.56GB다. 이 단계에서는 컨테이너 9개와 볼륨 4개가 그대로 유지됐다. Mac에서 공개 헬스 체크를 확인한 시각은 2026-09-05 15:36:39 KST 부근이며 HTTP 200, `status=UP`이었다.

### 2차 정리: API EC2 역할에 맞게 이전 구성 제거

사용자가 API EC2에는 Java·Caddy·Redis만 남기도록 요청했고, 기존 DB 볼륨 삭제도 명시적으로 승인했다. `docker inspect`로 `catchhole-postgres-1`의 `/var/lib/postgresql/data`에 연결된 볼륨이 `catchhole_postgres_data`임을 확인한 뒤, 사용자가 SSM에서 정리했다.

삭제한 이전 컨테이너 6개:

- `catchhole-ai-character-comparison-worker-1`
- `catchhole-ai-worker-1`
- `catchhole-ai-worker-2`
- `catchhole-ai-world-comparison-worker-1`
- `catchhole-postgres-1`
- hello-world 테스트 컨테이너

삭제한 API EC2 로컬 이미지:

- `ghcr.io/catchhole-soma/catchhole-backend-ai:main`
- `pgvector/pgvector:0.8.2-pg16`
- `postgres:16-alpine`
- `hello-world:latest`
- `public.ecr.aws/aws-cli/aws-cli:latest`

삭제한 데이터 볼륨: `catchhole_postgres_data`. 이번 정리 과정에서 DB 백업을 새로 만들지는 않았다. 별도 백업이 없으면 삭제한 로컬 DB 데이터는 복구할 수 없다. 삭제한 이미지는 동일 이미지가 레지스트리에 남아 있으면 다시 받을 수 있다. RDS와 Worker EC2에는 삭제 명령을 실행하지 않았다.

### 최종 상태 검증 — 2026-09-05 사용자 출력 기준

사용자가 마지막으로 전달한 `docker ps -a`, `docker image ls`, `docker volume ls`, 공개 헬스 체크 출력으로 확인했다.

- 컨테이너: `catchhole-backend-1`, `catchhole-caddy-1`, `catchhole-redis-1` 세 개만 존재하며 모두 실행 중. Redis는 `healthy`.
- 이미지: Caddy, Redis, Java의 `main`·`sha-383d2af`·`sha-6491f92`만 남음. 현재 Backend는 `sha-383d2af`를 사용하며 이전 SHA 이미지는 보존.
- 볼륨: `catchhole_caddy_config`, `catchhole_caddy_data`, 익명 볼륨 1개 유지. 익명 볼륨의 연결 대상은 이번 출력만으로 확정하지 않았으며 삭제하지 않음.
- `catchhole_postgres_data`는 최종 볼륨 목록에서 제거됨.
- `curl -fsS https://api.catchhole.com/actuator/health` 결과: `{"groups":["liveness","readiness"],"status":"UP"}`.
- 46%라는 디스크 사용률은 1차 이미지 정리 직후 측정값이다. 2차 정리 이후 디스크 사용량은 추가 측정하지 않았다.
