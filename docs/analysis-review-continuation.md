# 다음 회차 분석 전 검토와 후보 종료 (GH369)

새 설정 추출을 요청할 때 이전 회차의 직접 검토와 정상적인 애매함을 구분한다. 직접 검토 대상은 반영 또는 제외를 끝내야 하며, 캐릭터·세계관의 정상 보류는 경고를 확인하고 계속할 때만 종료한다. 관계 HOLD는 관계도에 노출하지 않고 다음 회차 분석 참고로 유지한다.

## 시작 흐름

1. Front가 선택한 회차 번호로 `POST /api/v1/works/{workId}/analysis-start-checks`를 호출한다. 업로드 전에도 사용할 수 있는 읽기 전용 확인이며 소유권을 검증한다.
2. 응답은 먼저 끝나야 할 이전 분석 수, 직접 검토 개수, 캐릭터·세계관의 종료 가능한 개수, 안내용 관계 HOLD 개수, `revision`이다. 정상 설정 보류 종료 대상은 새 요청의 최소 회차 번호보다 앞선 현재 출처의 후보다. 직접 검토와 이전 분석 진행 여부는 최대 대상 번호보다 앞선 회차까지 확인해, 앞 회차를 다회차 요청에 섞어 검토를 우회하지 못하게 한다. 설정집, 보관·교체된 원문, 같은 회차 후보는 이번 범위에 넣지 않는다.
3. 직접 검토가 남으면 검토 화면으로 안내한다. 애매한 설정 후보가 있으면 정확도가 낮아질 수 있고 계속할 때 목록과 이후 참고에서 제외됨을 알린다. 관계 HOLD는 종료하지 않고 후속 관계 분석에서 참고함을 별도로 안내한다.
4. 설정 후보 종료를 선택하면 기존 분석 생성 요청에 `closeAmbiguousCandidates=true`, `reviewGateRevision`을 보낸다. 관계 HOLD만 남았다면 두 필드 없이 생성한다. 서버가 실제 생성할 회차 목록을 다시 계산한다.
5. 서버는 Work 잠금 아래 원래 대상·활성 작업·원문 검증 뒤 후보 상태와 revision을 재확인한다. 새 직접 검토가 생기면 `ANALYSIS_MANUAL_REVIEW_REQUIRED`, 동의가 없으면 `ANALYSIS_REVIEW_ACKNOWLEDGEMENT_REQUIRED`, 범위·상태가 달라졌으면 `ANALYSIS_REVIEW_GATE_CHANGED`를 반환한다.
6. 이미 고정 입력을 가진 미완료 순차 실행이 있으면 기존 설정 변경 보호로 종료를 거절한다. 종료와 새 Job 생성·초기 입력 준비는 한 트랜잭션이다. 토큰 부족이나 입력 준비 실패 시 종료·감사 기록·새 Job 모두 롤백한다.

revision은 작품, 정렬·중복 제거한 전체 대상 회차 목록, 후보 ID·수정 시각·분류와 원 Job 상태, 관계 HOLD의 원본 참조·완료 hash를 묶은 SHA-256이다. API 소유권 검증을 대체하지 않으며, 다른 대상에 대한 확인이나 오래된 확인을 재사용하지 못하게 하는 값이다.

## 분류

| 데이터 | 처리 |
| --- | --- |
| 직접 검토 Job의 미확정 캐릭터·세계관 | 검토 필수. 반영 또는 제외까지 다음 분석 거절 |
| 자동 Job이어도 작가가 수정한 후보·명시적 전체 반영 보류 | 직접 결정 보호. 자동 종료하지 않음 |
| 완료된 자동 분석의 정상 REVIEW_REQUIRED·대상/값/시점 보류 | 경고 후 명시적 계속으로 종료 가능 |
| 완료된 관계 결과의 아직 소비되지 않은 정상 HOLD | 안내용. 관계도에 표시하지 않고 다음 회차 분석에 참고 |
| 비교 대기·처리 중·FAILED·재비교 필요·기술적 실패 사유 | 정상 애매함으로 종료하지 않음. 기존 처리·복구 정책 유지 |

현재 유효한 원본 Job을 scalar projection으로 확인한다. 후보마다 대형 Job 입력/journal JSON을 eager fetch하지 않는다. 관계 조회도 필요한 결정·바인딩만 읽으며 Job의 상태 JSON은 읽지 않는다.

## 보존과 후속 참고

- 캐릭터·세계관은 새 `CLOSED` 검토 상태와 `closedAt`, `closureRequestId`만 기록한다. AI 판단, 값, 인용, 비교·실패 기록은 바꾸지 않는다. 기본 검토 목록/집계와 PENDING_REVIEW 기반 후속 참고에서 제외하고, 명시적인 CLOSED 조회는 감사용으로 허용한다.
- 기존 `dismiss()`를 호출하지 않는다. 종료는 “틀린 주장”이라는 사용자 반려가 아니며 `HUMAN_REJECTION_POLICY`에 등록하지 않는다.
- 관계 HOLD는 시작 확인에서 `relationship_hold_closures`에 새 종료를 기록하지 않는다. 기존 보류 결정과 원문 근거를 다음 회차 관계 비교의 참고로 유지한다.
- `analysis_review_continuations`는 사용자·작품·안내 revision·시작 회차·종료한 설정 후보 수를 저장한다. 관계 종료 건수는 0이다. ID는 새 Job들의 `metricsRequestId`와 같아 종료 동의와 실행을 연결한다. 원문/후보 값은 복사하지 않는다.
- 종료된 후보를 다시 확정·수정하는 기존 mutation은 거절한다. 새로운 회차의 새 관측으로 다시 후보를 만드는 것은 막지 않는다.
- 이미 시작한 Job의 고정 입력과 완료된 후행 분석은 변경하지 않는다. 원문/작품 파기의 기존 보존 정책은 그대로 적용되며 종료 상태가 원문 파기를 면제하지 않는다.

## 경계와 배포

새 공개 `SETTING_EXTRACTION` 요청(신규 업로드, 저장된 업로드의 분석, 명시적 재분석)에 적용한다. 같은 Job 실패 재시도와 이미 예약한 다회차 묶음 내부는 기존 실행을 이어간다. 별도 신규 회차 **오류 검사** 접수와 그 검사 완료 후 내부 추출 release는 이번 새 설정 추출 동의 계약에 포함하지 않는다. 검사 시작 시점까지 확장하려면 그 접수 API의 동의·원자성 계약을 별도로 설계해야 한다.

앞 회차 반영에 따른 후행 관계 일괄 무효화 제거는 #367 / PR #368의 별도 변경이다. 이 PR은 그 정책을 대신 수정하지 않으며 **#368 → #370 → Front #118 순서**로 적용한다. 정상 관계 HOLD의 안내도 #368의 공개 세대 계약에 맞춰 실제 원문 불가만 전역 경계로 삼는다. 한 회차의 INVALIDATED는 해당 행을 제외하지만 무관한 뒤 회차 HOLD를 숨기지 않는다. 아직 공개하지 않은 백필 생성 세대는 안내·종료하지 않는다. 이 조합과 실제 원문 파기 경계를 별도 회귀로 확인한다.

V115는 후보 상태/종료 감사 컬럼, V116은 관계 종료, V117은 동의-새 실행 연결이다. 먼저 반영된 검수 기능의 V113·V114는 그대로 유지하며, 이 기능의 미배포 migration만 빈 번호로 옮겼다. Front는 서버 OpenAPI로 생성한 SDK를 사용한다. Backend 먼저 배포 후 Front를 배포한다. 구 Front도 동의 없이 후보를 종료할 수 없으며, 새 409를 일반 오류로 볼 수 있으므로 두 배포 간격을 줄인다. CLOSED 값이 생긴 뒤 구 enum만 아는 Backend로 단순 롤백하지 않는다.

## 검증

후보와 관계의 H2/PostgreSQL 통합 테스트는 분류·실제 조회·근거 보존·설정 후보의 후속 참고 제외·관계 HOLD의 후속 참고 유지·새 관측 허용을 확인한다. HTTP 테스트는 인증/소유권, 설정 후보 무동의 거절, 관계 HOLD만 남았을 때 무동의 진행, 대상에 묶인 revision, 경고 뒤 작가 수정, 설정 후보 종료와 새 Job의 연결, 생성 실패의 롤백을 확인한다. Front는 경고 취소·계속·직접 검토 차단·오래된 안내 재확인과 저장된 업로드 재사용을 검증한다. 실제 실행 결과는 PR에 기록하며 미실행을 통과로 간주하지 않는다.
