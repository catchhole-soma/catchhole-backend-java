# 관계도 탐색 (GH412)

## 표시와 조회

- 선택 회차의 유효한 관계가 300개 미만이고 인물이 100명 미만이면 전체 개요를 표시한다. 관계 300개 또는 인물 100명 이상이면 전체 인물 검색과 연결 인물 수 기준 추천으로 시작한다. 두 기준은 UX 기준이며 성능 한계 수치가 아니다.
- 중심 인물을 선택하면 직접 연결만 100개씩 조회한다. 페이지를 바꾸어 모든 연결에 접근할 수 있고, 한 번에 그리는 관계는 100개로 제한한다. 병렬 관계·종료 관계도 개별 항목으로 보존한다.
- 검색은 초기 개요에 포함되지 않은 인물까지 대상으로 하며 회차·작품·공개 세대와 원문 유효성을 적용한다. 추천 순서는 서로 다른 연결 인물 수, 이름, ID 순이다. 동명이인은 합치지 않는다.
- URL은 회차·중심 인물·연결 페이지를 보존한다. 검색은 조합 입력 종료 후 지연 조회하고 이전 요청을 취소한다. 완료된 관계도는 주기적으로 다시 조회하지 않는다.

## 서버 경계

기존 API를 유지하고 탐색용 읽기 경로를 별도로 제공한다. PostgreSQL에서 최신 공개 분석과 최신 관계를 고른 후 필요한 열·행만 반환한다. 분석의 context/bindings/decisions와 원문 인용 전체를 Java 엔티티로 올리지 않는다. 실패·보류 판단에 필요한 참조만 DB에서 추출하며, 인용은 선택한 관계의 상세 조회에서만 반환한다. 모든 탐색 읽기는 소유권 확인 뒤 REPEATABLE READ로 수행한다.

기존 원문 교체·파기 경계, 공개 백필 세대, 별칭 노드 연결, 사용자 정정·숨김, 기술적 미완료와 의미상 보류 구분을 보존한다. 현재 프로필 이름 표시 규칙은 기존 API와 같고, 검색 별칭은 선택 회차까지 확인된 이름만 사용한다.

## 검증

실제 PostgreSQL에서 299/300개 경계, 200개 밖 검색, 원문 무효화, 다른 작품·미래 회차, 리다이렉트·보류·실패, 페이지 중복/누락을 검증한다. 합성 데이터의 쿼리 수·실행 계획·응답 크기·시간을 기록하고 운영 실측과 구분한다. 운영 데이터와 AI 실행에는 변경을 가하지 않는다.

## API

| GET 경로 (`/api/v1/works/{workId}/relationship-graph` 아래) | 입력 | 반환 |
| --- | --- | --- |
| `/explore` | `episodeNo?`, `focusNodeId?`, `page=0` | 작은 개요 또는 선택 화면, 중심 관계 100개 페이지, 전체 인물/관계 수 |
| `/people` | `episodeNo?`, `query`, `page=0`, `size=20` (최대 50) | 전체 유효 인물의 이름·확정 별칭 검색, 다음 페이지 여부 |
| `/explore/edges/{edgeId}` | `episodeNo?` | 선택한 연결과 유효한 원문 인용 |

페이지는 0부터 시작한다. 중심 인물 없이 0 이외 페이지는 400, 존재하지 않는 인물·회차·관계는 404다. 검색 `%`, `_`는 패턴으로 확장하지 않는다. 문맥 없는 동명이인을 묶지 않는다. 다른 작품의 인물 ID는 해당 작품의 탐색 조건을 통과하지 못한다.

각 공개 읽기는 소유권 확인과 원문 hash/key/version·파기 요청·공개 백필 세대 검사 뒤 수행한다. 최신 이벤트만 선택하고, 노드 리다이렉트는 기존과 같은 최대 8단계로 해소한다. 명시된 별칭은 유효한 원문에서 확정한 후보만 검색한다. 기존 API는 구 클라이언트와의 호환을 위해 유지한다.

## 성능 확인 (2026-11-10)

PostgreSQL 16 Testcontainers에 합성 198회차, 인물 3,130명, 관계 3,129개를 만들고 분석 문맥에 40,000자 합성 문자열을 넣었다. 워밍업 2회 후 5회 측정한 Spring 서비스 평균은 기존 200개 조회 116.7ms, 새 초기 선택 29.4ms, 중심 관계 100개 조회 57.7ms, 이름 검색 29.4ms였다. HTTP/인터넷·LLM 시간은 제외하며 운영 성능이나 정확도 지표가 아니다.

- 기존 읽기의 Hibernate prepared statement는 603회였다. 새 초기 선택은 소유권을 포함해 4회, 중심 조회는 10회 이하로 계측됐다. 새 수는 JDBC 오버로드의 내부 위임을 포함하는 보수적 상한이다.
- 직렬화한 DTO는 기존 110,575B, 새 초기 선택 16,975B, 중심 100개 63,557B였다. HTTP envelope·압축은 제외한다. 새 초기 화면은 전체 선을 그리지 않으므로 같은 정보를 한 번에 보내는 비교는 아니다.
- 전체 분석/원문 JSON을 엔티티로 읽지 않고, 인물별 반복 집계를 한 번의 집합 집계로 바꿨다. 재귀 결과 수의 과대 추정을 피하도록 최대 깊이가 고정된 PK 조인을 사용했다. 실행 계획에서 사용 중인 PK와 작품별 인덱스를 확인했으며 신규 운영 인덱스나 저장 카운터는 추가하지 않았다.
- 근거 인용은 선택한 관계의 상세에서만 반환한다. 목록은 해당 페이지의 근거 개수만 집계한다. 여전히 회차/관계 메타데이터의 DB 집계가 있으므로 무제한 규모에 일정한 시간이 보장되는 구조는 아니다.

원본은 `docs/load-tests/gh412-explorer-samples.json`, `docs/load-tests/gh412-explorer-query-plan.txt`에 보존한다. 별 모양 구조의 프런트 계산에서는 201명/200개 개요 3,909ms, 300명/299개 개요 17,240ms, 중심 101명/100개 1.67ms(각 예열 2회+5회 평균)를 확인해 인물 100명 기준도 추가했다. 이 값은 로컬 Node 배치/선 계산만 포함하며 브라우저 DOM/paint와 서버 측정값에 합산하지 않는다.

## 배포와 검증

서버를 먼저 배포한 뒤 생성 SDK가 포함된 프런트를 배포한다. DB 마이그레이션·AI 재분석·운영 원고 변경은 없다. 프런트를 이전 버전으로 되돌리면 기존 API를 계속 사용할 수 있다.

- PostgreSQL 통합 테스트는 기존 관계도 시나리오마다 새 조회의 회차·상태·인물·관계·인용을 대조한다. 299/300개, 인물 99/100명, 100개 페이지, 전체 검색, 리다이렉트, 사용자 정정, 숨김, 파기·교체, 기술적 실패와 의미상 보류를 검증한다.
- `GH412_FIXTURE_OUTPUT=/tmp/gh412-explorer-contract.json ./gradlew test --tests '*EpisodeRelationshipGraphPostgresIntegrationTest'`는 실제 MVC 응답과 인증/잘못된 입력/없는 회차 상태 코드를 검증하고 프런트 계약 테스트용 응답을 저장한다. 프런트는 이를 그대로 재생하며 운영 서버 연결 검증으로 표현하지 않는다.
